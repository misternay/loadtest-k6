บทที่ 6 จาก 6

อ่านผลลัพธ์ให้ออก และไม่สรุปผิด

เมื่อการรันจบ k6 พิมพ์ข้อมูลหลายสิบบรรทัดรวดเดียว จุดที่คนอ่านผิดบ่อยที่สุดคือกับดักของ http_req_failed และ p99 ที่ไม่ปรากฏโดยค่าเริ่มต้น

ใช้เวลาอ่านประมาณ 15 นาที
ต้องอ่านก่อน: บทที่ 3
ต่อจากนี้: แก้ปัญหาที่พบบ่อย

ใจความสำคัญ

  1. threshold ที่ไม่ผ่านทำให้ k6 จบด้วย exit code 99 จึงใช้กั้นไปป์ไลน์ได้ทันที
  2. p99 ไม่ปรากฏบนหน้าจอสรุปผลโดยค่าเริ่มต้น ต้องเพิ่มด้วย --summary-trend-stats หรือส่งข้อมูลดิบมาคำนวณเอง
  3. ผลของ check() ไม่ทำให้การรันล้มเหลวถ้าไม่มี threshold คุม metric checks
  4. smoke test ควรใช้เพดานสุขภาพที่หลวมกว่าเกณฑ์ SLO เพราะตัวอย่างน้อยเกินไป

ลำดับการอ่าน: สองบรรทัดแรกตัดสินทุกอย่าง

k6 พิมพ์ metric เรียงตามชื่อ ไม่ได้จัดกลุ่มเป็นห้ากลุ่มตามหัวข้อ ด้านล่างจึงเป็น ลำดับการอ่านที่เราตั้งขึ้น

อ่านบล็อก EXECUTION ก่อนเสมอ ถ้าการรันไม่สมบูรณ์ ตัวเลขที่เหลือไม่มีความหมาย

  1. บล็อก EXECUTION — บรรทัดที่ขึ้นต้นด้วย running (…) บอกว่าการรันจบครบไหม มีรอบใดถูกขัดจังหวะหรือไม่ ถ้าที่นี่ผิดปกติ ตัวเลขที่เหลือทั้งหมดไม่ต้องอ่านต่อ
  2. บล็อก THRESHOLDS — สรุปว่าเกณฑ์ที่ตั้งไว้ผ่านหรือไม่ เป็นบรรทัดที่มีผลต่อ exit code และต่อไปป์ไลน์อัตโนมัติ
  3. บล็อก checks — สัดส่วนการตรวจเงื่อนไขทางธุรกิจที่ผ่าน
  4. บล็อก HTTP — metric หลักของคำขอ ได้แก่จำนวน อัตราความผิดพลาด และเวลาตอบสนอง พร้อม sub-metric ที่แยกเวลาออกเป็นส่วน
  5. บล็อก NETWORK — ปริมาณข้อมูลที่ส่งและรับ ใช้ตรวจว่าเรากำลังวัดสิ่งที่คิดว่ากำลังวัดอยู่จริง
ทำไมต้องเริ่มที่ EXECUTION

ถ้าการรันถูกขัดจังหวะกลางทาง หรือ VU ทำงานไม่ครบตามที่ตั้งไว้ ตัวเลข p95 ที่สวยงาม ก็มาจากข้อมูลเพียงครึ่งเดียว การอ่านตัวเลขประสิทธิภาพก่อนตรวจว่าการรันสมบูรณ์หรือไม่ เป็นสาเหตุอันดับต้น ๆ ของการสรุปผิด

บล็อก THRESHOLDS

บล็อกนี้ปรากฏเฉพาะเมื่อสคริปต์ตั้ง thresholds ไว้ ถ้าไม่มี บรรทัดนี้หายไป ทั้งบล็อก ซึ่งไม่ได้แปลว่าอะไรผิด เมื่อ threshold ไม่ผ่าน k6 จบด้วย exit code 99 ซึ่งแยกจากความล้มเหลวเพราะสคริปต์ผิดพลาด จึงใช้กั้นไปป์ไลน์ได้

ความหมายของสิ่งที่เห็นในบล็อก THRESHOLDS
สิ่งที่เห็น อ่านว่าอะไร
เครื่องหมายถูกนำหน้าบรรทัดเกณฑ์ เกณฑ์ข้อนั้นผ่าน — ตัวเลขที่ตามมาคือค่าจริงที่วัดได้ ณ ตอนตัดสิน
เครื่องหมายกากบาทนำหน้าบรรทัดเกณฑ์ เกณฑ์ข้อนั้นไม่ผ่าน และ k6 จะจบด้วย exit code 99
เกณฑ์ที่เขียนว่า { p(95)<500 } เงื่อนไขที่ตรวจ พร้อมค่าจริงที่ใช้ตัดสิน
aborted การรันถูกหยุดกลางทางเพราะเกณฑ์ที่ตั้ง abortOnFail ไว้ไม่ผ่าน — ข้อมูลที่ได้จะไม่ครบช่วง
ตัวอย่างเกณฑ์ที่ผ่านจริง

ในการรันที่ตั้ง http_req_duration: ['p(95)<500'] ไว้ k6 รายงานว่าเกณฑ์นี้ผ่าน โดยวัดค่า p(95) ได้ 28.39 มิลลิวินาที ซึ่งต่ำกว่าเพดาน 500 มิลลิวินาทีอยู่มาก ตัวเลข 28.39 ms เป็นผลการรันจริงคนละครั้งกับชุดข้อมูล 1,155 ค่าในบทที่ 4 เพราะการรันนั้นใช้จำนวน VU และอัตราที่ต่างกัน

บล็อก checks

check() คือการตรวจเงื่อนไขทางธุรกิจที่เราเขียนเอง ผลของ check ไม่ทำให้การรันล้มเหลว ถ้าไม่มี threshold คุม metric checks

check ที่มีค่าจริง เพราะมี threshold คุม 
import { check } from 'k6';
import http from 'k6/http';

export const options = {
  thresholds: {
    // ถ้าไม่ใส่บรรทัดนี้ ผลของ check จะเป็นเพียงข้อมูลประกอบ ไม่มีผลต่อ exit code
    checks: ['rate>0.99'],
  },
};

export default function () {
  const res = http.get(`${BASE_URL}/api/items`);

  check(res, {
    'สถานะเป็น 200':        (r) => r.status === 200,
    'ได้รายการไม่ต่ำกว่า 20': (r) => JSON.parse(r.body).count >= 20,
    'ชื่อสินค้าไม่ว่าง':      (r) => JSON.parse(r.body).items.every((i) => i.name.length > 0),
  });
}

การรันที่เป็นหลักฐานของบทเรียนนี้ไม่ได้เขียน check() ไว้ จึงไม่มีบรรทัด checks และไม่มีเครื่องหมายกำกับ http_req_failed

บล็อก HTTP

อ่านคู่กัน โดยเริ่มจากอัตราความผิดพลาด แล้วจึงดูเวลา

การอ่านบล็อก HTTP ตามลำดับ พร้อมค่าจากการรันจริง
ลำดับ บรรทัด อ่านว่าอะไร ค่าจริงในการรันนี้
1 http_req_failed มีคำขอที่ล้มเหลวกี่เปอร์เซ็นต์ ถ้าเกิน 1% ให้หยุดอ่านบรรทัดอื่นแล้วหาสาเหตุก่อน 0.00% — ไม่มีคำขอใดล้มเหลวเลยจาก 1,155 คำขอ
2 http_reqs ยอดสะสมและอัตราต่อวินาที ใช้เป็น throughput ของการรันนี้ 1,155 คำขอ ที่ 93.44 คำขอต่อวินาที
3 http_req_duration เวลาตอบสนอง ดู avg กับ p(95) พร้อมกัน ถ้าต่างกันมากแปลว่ามีหาง avg 54.25 ms · med 44.40 ms · p(90) 65.31 ms · p(95) 74.53 ms · max 584.70 ms
4 http_req_waiting เวลาที่รอเซิร์ฟเวอร์ ถ้ากินสัดส่วนมากสุด แปลว่าคอขวดอยู่ที่เซิร์ฟเวอร์ avg 54.03 ms คิดเป็น 99.58% ของเวลาต่อคำขอ
5 http_req_blocked
http_req_connecting		 เวลาฝั่งเครื่องทดสอบ ถ้าสูงแปลว่าปัญหาอยู่ที่ฝั่งเรา ไม่ใช่ฝั่งเซิร์ฟเวอร์ avg 0.02 ms และ 0.01 ms — แทบไม่มีเลย
6 http_req_sending
http_req_receiving		 เวลาส่งคำขอและรับคำตอบ ขึ้นกับขนาดข้อมูลและคุณภาพเครือข่าย avg 0.05 ms และ 0.17 ms — น้อยมาก

กับดักที่อันตรายที่สุด: http_req_failed กับ 4xx

k6 นับสถานะ 4xx เป็นความล้มเหลวโดยค่าเริ่มต้น ซึ่งถูกต้องสำหรับ endpoint ที่ควรตอบ 200 แต่ผิดสำหรับการทดสอบที่ตั้งใจยิงไปยัง endpoint ที่ควรตอบ 404 ถ้าไม่ใช้แท็ก expected_response อัตราความล้มเหลวที่เห็นจะสูงเกินจริง และถ้าใช้แท็กนั้นแล้วไม่เขียน check() กำกับ ปัญหาจริงก็จะถูกกลบไปอีกทางหนึ่ง

กับดักที่สอง: k6 ไม่แสดง p99 ให้โดยค่าเริ่มต้น

สรุปผลมาตรฐานของ Trend แสดงเพียง avg, min, med, max, p(90) และ p(95) เท่านั้น ค่า p99 ที่หลายทีมใช้เป็นเกณฑ์จะไม่ปรากฏบนหน้าจอ ถ้าไม่ได้ตั้ง threshold ที่อ้างถึง p(99) ไว้ หรือไม่ได้ส่งออกข้อมูลดิบออกมาคำนวณเอง ตัวเลข p99 466.29 ms ที่ใช้ในบทที่ 4 มาจากการคำนวณบนข้อมูลดิบทั้ง 1,155 ค่า จากไฟล์ที่ส่งออกด้วย -o csv=… ไม่ได้มาจากหน้าจอสรุปผล

ส่งออกผลไปทำกราฟต่อ

หน้าจอสรุปไม่พอเมื่อต้องเทียบหลายรอบ ต้องส่งออกข้อมูลดิบแล้วคำนวณเอง

คำสั่งส่งออกผลในรูปแบบต่าง ๆ 
# 1) สรุปผลแบบสั้น สำหรับอ่านบนหน้าจอหรือบันทึกในบันทึกการรัน
k6 run --summary-mode compact -e BASE_URL=http://localhost:8080 load.js

# 2) สรุปผลเป็นไฟล์ JSON เพื่อเทียบระหว่างรอบด้วยสคริปต์
k6 run --summary-export=summary.json load.js

# 3) ข้อมูลดิบรายคำขอเป็น CSV เปิดในสเปรดชีตได้ทันที
k6 run -o csv=raw.csv load.js

# 4) ข้อมูลดิบเป็น JSON พร้อม tags ครบ สำหรับวิเคราะห์เชิงลึก
k6 run -o json=raw.json load.js

ไฟล์ CSV มีหนึ่งบรรทัดต่อหนึ่งค่าที่วัดได้ จึงสร้างฮิสโตแกรมได้ตรงไปตรงมา

วิธีที่สาม: ขอให้ k6 แสดง p99 บนหน้าจอ

ตัวเลือกที่เปลี่ยน สิ่งที่พิมพ์บนหน้าจอสรุปผล ชื่อ --summary-trend-stats

ขอให้ k6 แสดง p50, p99 และ p99.9 เพิ่ม 
k6 run --summary-trend-stats="avg,min,med,max,p(50),p(90),p(95),p(99),p(99.9)" k6/smoke.js

ค่าเริ่มต้นของ k6 คือ avg, min, med, max, p(90), p(95) ซึ่งไม่มี p99 และไม่มี p50 เมื่อใส่ตัวเลือกนี้บรรทัด http_req_duration จะเปลี่ยนไปดังนี้

เทียบบรรทัด http_req_duration ก่อนและหลังใส่ตัวเลือก 
# ก่อน — ค่าเริ่มต้น ไม่มี p(50) และไม่มี p(99)
http_req_duration..............: avg=35.09ms min=7.15ms med=37.68ms max=47.94ms p(90)=46.35ms p(95)=46.91ms

# หลัง — มี p(50), p(99) และ p(99.9) เพิ่ม
http_req_duration..............: avg=30.55ms min=8.7ms med=32.73ms max=49.58ms p(50)=32.73ms p(90)=42.94ms p(95)=44.84ms p(99)=47.79ms p(99.9)=49.4ms

ที่มา: การรันจริงสองครั้งบน k6 v2.2.0 ด้วย k6/smoke.js (2 VU, 20 วินาที) สิ่งที่ควรดูคือชุดสถิติที่ปรากฏ ไม่ใช่ค่าตัวเลข ผลดิบอยู่ที่ docs/evidence/k6-summary-trend-stats.txt

  • มันเปลี่ยนแค่สิ่งที่พิมพ์ ไม่ได้เปลี่ยนวิธีคำนวณ สถิติเดิมเท่าเดิม
  • มันมีผลกับทุก Trend metric ไม่ใช่เฉพาะ http_req_duration iteration_duration ได้สถิติชุดเดียวกัน
  • มันไม่เปลี่ยนผลการตัดสิน threshold

เลือกวิธีไหน

เทียบตัวเลือกการนำผลออกทั้งสี่แบบ
ตัวเลือก เปลี่ยนอะไร ได้ p99 ไหม เหมาะเมื่อ
(ไม่ใส่) – ไม่ได้ ดูผลเร็ว ๆ ระหว่างพัฒนา
--summary-trend-stats สิ่งที่พิมพ์บนหน้าจอสรุป ได้ บนหน้าจอ อยากเห็น p99 ทันทีโดยไม่ต้องเก็บไฟล์
--summary-export=ไฟล์ เขียนสรุปผลเป็นไฟล์ JSON (หน้าจอไม่เปลี่ยน) ได้ ถ้าใส่ --summary-trend-stats ควบไปด้วย ต้องเทียบหลายรอบด้วยสคริปต์
-o csv / -o json ส่งข้อมูลรายคำขอออกเป็นไฟล์ ได้ แต่ต้องคำนวณเอง ต้องวิเคราะห์เชิงลึก เลือกช่วงเวลา หรือกรอง tag เอง
threshold ที่อ้าง p(99) ผลการตัดสินผ่าน/ไม่ผ่าน (ค่าปรากฏในบล็อก THRESHOLDS) ได้ และผูกกับการตัดสิน ต้องให้ไปป์ไลน์ตัดสินด้วย p99 ไม่ใช่แค่รายงาน

ทำ smoke test ก่อนเสมอ

ขั้นตอนนี้ใช้เวลาไม่ถึงครึ่งนาที แต่ประหยัดเวลาได้เป็นชั่วโมง เมื่อพบตอนนาทีที่สิบว่า ลืมใส่ header ยืนยันตัวตน

รัน smoke test ก่อนทุกครั้ง 
# ยืนยันว่าปลายทางตอบและสคริปต์ถูก — 10 วินาทีก็พอ
k6 run -e BASE_URL=http://localhost:8080 examples/smoke.js

# ถ้าผ่าน จึงค่อยรันการทดสอบจริง
k6 run -e BASE_URL=http://localhost:8080 examples/load.js
  • URL หรือพาธผิด ได้ 404 ทุกคำขอ
  • ลืม header ยืนยันตัวตน ได้ 401 ทุกคำขอ
  • ปลายทางไม่ทำงาน หรือรัน mock server คนละพอร์ต
  • ไวยากรณ์ใน check() ผิด หรือเรียกค่าจาก response ที่ไม่มีอยู่จริง

ทำไม smoke จึงไม่ควรใช้เกณฑ์เดียวกับ load test

ตอนแรก smoke.js ตั้ง vus: 1, duration: '10s' และใช้เกณฑ์เดียวกับ load test คือ p(95)<500 กับ checks>0.99 ผลคือ **รัน 37 ครั้ง ไม่ผ่าน 6 ครั้ง (16%)**

สาเหตุข้อแรกคือ จำนวนตัวอย่างน้อยเกินไป 1 VU กับ sleep(1) ใน 10 วินาที เก็บได้ราว 9 รอบ = 27 ข้อตรวจ เมื่อ check ตก 1 ข้อ อัตรากลายเป็น 26/27 = 96.3% ต่ำกว่าเกณฑ์ 99% ทันที และ p(95) ของชุดเล็กคือค่าที่สองจากท้าย

ข้อที่สองคือ ปลายทางจำลองมีหางยาวปนอยู่ mock server ของโปรเจกต์เคย เปิดหางยาว 3% ไว้ตลอด (บางคำขอช้าลง 150–570 ms) ขัดกับเกณฑ์ที่บังคับให้ทุกคำขอเร็ว

mock server ในโปรเจกต์นี้มีสองโหมดบทบาท
  • โหมดประพฤติดี (ค่าเริ่มต้น) — node mock-server/server.mjs ตอบทุกคำขอในราว 6–46 ms ไม่มีหางยาว ใช้เป็นปลายทางอ้างอิงที่มั่นคงสำหรับชุดทดสอบทั้งหมด
  • โหมดหางยาว — TAIL_RATE=0.03 node mock-server/server.mjs ทำให้ 3% ของคำขอ ช้าลง 150–570 ms ใช้เมื่อต้องการสาธิตว่าเปอร์เซ็นไทล์ตอบสนองต่อหางยาวอย่างไร อย่าใช้ปลายทางในโหมดนี้เป็นตัวกั้นชุดทดสอบ เพราะเกณฑ์ของสคริปต์ตั้งไว้สำหรับปลายทางที่ประพฤติดี

ตรวจได้ว่าตอนนี้อยู่โหมดใดด้วย curl -s http://localhost:8080/health แล้วดูค่า tailRate (0 = โหมดประพฤติดี)

ทางแก้คือแยกหน้าที่ให้ชัด smoke ไม่ได้ตัดสิน SLO คำถามเดียวคือ "สคริปต์กับปลายทางยังทำงานไหม"

สิ่งที่แก้ใน smoke test และเหตุผล
แก้เป็น เหตุผล
vus: 2
duration: '20s'		 ได้ราว 40 รอบ = 120 ข้อตรวจ ทำให้ทั้ง p(95) และอัตรา check มีความหมายในระดับของ smoke และ check ที่ตก 1 ข้อไม่ทำให้ทั้งชุดล้มทันที
p(95)<1000 เป็น "เพดานสุขภาพ" ที่ตรวจว่า "ตอบได้ไหม" ไม่ใช่เกณฑ์ SLO ส่วนเกณฑ์ 500 ms ยังอยู่ที่ load.js และ soak.js
mock server ปิดหางยาวเป็นค่าเริ่มต้น ให้ smoke และ load ใช้ปลายทางที่คาดเดาได้ และเปิดหางยาวเฉพาะเมื่อต้องการสอนเรื่องเปอร์เซ็นไทล์

หลังแก้แล้ว รัน k6 run k6/smoke.js ซ้ำ 30 ครั้งผ่านทั้งหมด 30/30 ครั้งที่ 25 เครื่องหยุดชะงักจน p(95) ถึง 465 ms แต่ยังผ่าน เพราะเพดาน 1000 ms ถ้าใช้เกณฑ์ 500 ms จะล้มทันที ผลดิบอยู่ที่ docs/evidence/k6-smoke-repeatability.txt

หลักที่ควรจำ: ถ้าปลายทางมีหางยาวจริง อย่ารันซ้ำจนกว่าจะผ่าน ให้ผ่อน เกณฑ์ smoke ให้สะท้อนพฤติกรรมจริง แล้วเก็บเกณฑ์ SLO ไว้ใน load test

จริยธรรมและความปลอดภัยในการทดสอบโหลด

โหลดเทสต์คือการยิงคำขอจำนวนมากด้วยความเร็วสูง เครื่องมือเดียวกันใช้โจมตีระบบได้ ผลต่อปลายทางเหมือนกัน ต่างแค่เจตนาและสิทธิ์

หลักที่ต้องยึด
  1. ยิงเฉพาะระบบที่เราได้รับอนุญาตให้ทดสอบ การทดสอบระบบของผู้อื่นโดยไม่ได้รับอนุญาตเข้าข่ายการโจมตีและอาจผิดกฎหมาย
  2. เลือกใช้สภาพแวดล้อมทดสอบก่อนเสมอ ไม่ใช่ระบบที่ผู้ใช้จริงกำลังใช้งานอยู่
  3. ตกลงขอบเขตและช่วงเวลาล่วงหน้า กับผู้ดูแลระบบปลายทาง เพราะโหลดเทสต์อาจกระทบผู้ใช้ร่วมระบบ
  4. เริ่มจากเล็กเสมอ ใช้ smoke test ก่อน แล้วค่อยเพิ่มภาระ เพื่อไม่ให้เกิดภาระกระชากที่ไม่ได้ตั้งใจ
  5. เตรียมวิธีหยุดฉุกเฉินไว้ รู้ว่าต้องกดอะไรเพื่อหยุดกลางทาง และรู้ว่าใครต้องแจ้งเมื่อเกิดปัญหา
  6. ระวังข้อมูลส่วนบุคคล อย่าใช้ข้อมูลผู้ใช้จริงในสคริปต์ทดสอบ และอย่าเก็บผลลัพธ์ที่มีข้อมูลอ่อนไหวไว้โดยไม่ป้องกัน

ตัวอย่างทุกตัวจึงชี้ไปที่ http://localhost:8080 หรือ https://test.k6.io ที่ผู้พัฒนา k6 สร้างเพื่อการทดสอบ สคริปต์ยังตรวจปลายทาง ก่อนรัน ถ้าไม่อยู่ในรายการที่อนุญาตจะหยุดทันที

สรุปบทที่ 6

  • อ่าน running (…) ก่อน ถ้าการรันไม่สมบูรณ์ ตัวเลขที่เหลือไม่มีความหมาย
  • THRESHOLDS กำหนด exit code 99
  • ผลของ check() ไม่ทำให้การรันล้มเหลวถ้าไม่มี threshold คุม checks
  • อ่านอัตราความผิดพลาดก่อนเวลา ระวังกับดัก 4xx
  • p99 มาจาก --summary-trend-stats, threshold p99 หรือข้อมูลดิบ
  • --summary-trend-stats · --summary-export · -o csv= คนละชั้นกัน
  • รัน smoke ก่อน และยิงโหลดเฉพาะระบบที่อนุญาต
