เลือกรูปแบบการทดสอบให้ตรงกับคำถามที่ต้องตอบ

รูปแบบการทดสอบไม่ใช่เรื่องของรสนิยม แต่เป็นการเลือกว่าจะถามคำถามอะไรกับระบบ

ใช้เวลาอ่านประมาณ 19 นาที
ต้องอ่านก่อน: บทที่ 2, บทที่ 4
สคริปต์จริง: ตัวอย่างทั้ง 5 แบบ

ใจความสำคัญ

  1. แต่ละรูปแบบตอบคำถามคนละข้อ — smoke ตรวจว่าสคริปต์และปลายทางยังทำงาน, load ยืนยันที่ภาวะเป้าหมาย, stress หาจุดอิ่มตัว, spike ดูการรับภาระกระชากและการฟื้นตัว, soak ดูการสะสมตามเวลา, breakpoint หาความจุสูงสุด
  2. ข้อมูลช่วงอุ่นเครื่องยังถูกนับรวมในสรุปท้ายการรันเสมอ ช่วงภาวะคงตัวจึงเป็นช่วงเดียวที่ตัวเลขนำไปตัดสินผลได้
  3. การแยกช่วงภาวะคงตัวเป็น scenario ของตัวเองแล้วอ้างแท็ก scenario ให้ตัวเลขที่สะอาดจริง ส่วน delayAbortEval เพียงเลื่อนเวลาที่ k6 จะตัดสินใจหยุด
  4. SLO ที่เขียนให้วัดได้แปลงเป็น threshold ได้ตรงตัว และควรตั้ง abortOnFail เฉพาะเกณฑ์ที่แปลว่าระบบกำลังพัง

ย้อนดู: สี่คำที่ต้องจำ (VU · RPS · RT · Budget)

รูปแบบการทดสอบทั้งหกแบบ

เริ่มจาก smoke เสมอ แล้วไล่ตามคำถามที่โตขึ้น

เทียบรูปแบบการทดสอบทั้งหกแบบ
รูปแบบ คำถามที่ตอบ ตั้งค่าอย่างไร สิ่งที่ได้เรียนรู้
smoke สคริปต์ถูกไหม ปลายทางยังตอบอยู่ไหม 2 VU นาน 20–30 วินาที ใช้เกณฑ์แบบ "เพดานสุขภาพ" ไม่ใช่เกณฑ์ SLO ข้อผิดพลาดพื้นฐานทั้งหมด เช่น URL ผิด ลืม header หรือ check ที่ไม่มีทางผ่าน
load ที่ภาวะใช้งานตามที่คาดไว้ ระบบยังทำได้ตามสัญญาไหม ไต่ขึ้นถึงระดับเป้าหมาย แล้วถือไว้ 5–20 นาที ตัวเลข p95 และอัตราความผิดพลาดที่ภาวะเป้าหมาย ใช้ยืนยันก่อนเปิดตัว
stress จุดอิ่มตัวอยู่ตรงไหน และพังแบบไหน ไต่ขึ้นเป็นขั้นจนเกินภาวะปกติ 2–4 เท่า จำนวนผู้ใช้สูงสุดที่รับได้ และรูปแบบการพัง เช่นตอบ 503 หรือเริ่มหมดเวลา
spike รับภาระที่กระโดดขึ้นกะทันหันได้ไหม และฟื้นตัวเร็วแค่ไหน กระชากขึ้นใน 10–30 วินาที ถือสั้น ๆ แล้วลดลง พฤติกรรมการต่อคิว การทิ้งคำขอ และเวลาที่ latency กลับสู่ระดับเดิม
soak ทนยาวไหม มีอะไรสะสมขึ้นตามเวลา ถือภาวะปกติต่อเนื่อง 1–4 ชั่วโมงขึ้นไป รอยรั่วหน่วยความจำ connection ที่ไม่ถูกคืน และการเสื่อมสภาพทีละน้อย
breakpoint ความจุสูงสุดที่ยอมรับได้คือเท่าไร เพิ่มขึ้นเป็นขั้นละ 10–20% จนตัวชี้วัดเริ่มผิดเกณฑ์ ตัวเลขความจุที่อ้างอิงได้ พร้อมเหตุผลว่าอะไรคือคอขวดที่แท้จริง
ลำดับการรันที่แนะนำ

smoke → load → stress → soak สำหรับงานประจำ เพิ่ม spike กับ breakpoint เมื่อสถาปัตยกรรมเปลี่ยนหรือเตรียมรับทราฟฟิกก้อนใหญ่ การข้าม smoke ไปรัน load ทันทีทำให้เสียเวลามากที่สุด เพราะถ้าสคริปต์ผิด จะได้ข้อมูลที่ตีความไม่ได้

ช่วงต่าง ๆ ของการรัน และช่วงที่ข้อมูลมีความหมาย

การรันที่ดีมีสี่ช่วง แต่ละช่วงมีบทบาทต่างกัน

  1. ช่วงอุ่นเครื่อง ระบบยังคอมไพล์โค้ด เติม cache ข้อมูลช่วงนี้ ช้ากว่าความจริงและไม่ควรนำไปตัดสินอะไร
  2. ช่วงไต่ขึ้น จำนวนผู้ใช้เพิ่มทีละขั้น เห็นได้ว่าระบบเริ่มตึงที่จุดไหน
  3. ช่วงภาวะคงตัว จำนวนผู้ใช้คงที่ เป็นช่วงเดียวที่ข้อมูลมีความหมาย ควรยาวพอที่จะเก็บข้อมูลได้อย่างน้อยหลายพันคำขอ
  4. ช่วงผ่อนลง ลดผู้ใช้เป็นขั้นตอนเพื่อให้คำขอที่ค้างอยู่ทำงานจนจบ
stages ที่มีครบทั้งสี่ช่วง 
export const options = {
  scenarios: {
    load: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '1m',  target: 3  },   // ช่วงอุ่นเครื่อง — ยังไม่ต้องอ่านค่า
        { duration: '2m',  target: 6  },   // ช่วงไต่ขึ้น
        { duration: '5m',  target: 10 },   // ภาวะคงตัว เริ่มนับข้อมูลจริง
        { duration: '3m',  target: 10 },   // ต่ออีก 3 นาที เพื่อยืนยันว่าเสถียร
        { duration: '1m',  target: 0  },   // ช่วงผ่อนลง
      ],
      gracefulRampDown: '30s',
    },
  },
  thresholds: {
    http_req_duration: [{
      threshold: 'p(95)<500',      // เกณฑ์ SLO ของระดับโหลดนี้
      abortOnFail: true,           // ถ้าไม่ผ่าน ให้หยุดการรันก่อนเวลาที่เหลือ
      delayAbortEval: '180s',      // แต่ยังไม่ต้องตัดสินใจหยุดใน 3 นาทีแรก
    }],
    http_req_failed: ['rate<0.01'],
  },
};

delayAbortEval เป็นชื่อตัวเลือกที่ถูกต้องของ k6 v2.2.0 (คู่กับ abortOnFail: true ในรูปแบบยาว) มันทำอย่างเดียวคือ เลื่อนเวลาที่ k6 จะตัดสินใจหยุดการรัน นับเป็นวินาทีจากเริ่มการรัน

สิ่งที่ delayAbortEval ไม่ได้ทำ คือตัดข้อมูลช่วงอุ่นเครื่อง ออกจากการคำนวณค่า threshold ค่า p(95) ที่ k6 รายงานท้ายการรัน ในการรันจริง ที่ตั้ง 20.1 วินาทีกับที่ไม่ได้ตั้ง รายงาน p(95) 603.32 ms กับ 602.49 ms เท่ากันในทางปฏิบัติ ทั้งที่ 10 วินาทีแรกของทั้งสองรันถูกทำให้ตอบช้า 600 ms ถ้ากรองข้อมูลได้ ค่าของรันที่ตั้งไว้ต้องเหลือราว 25–45 ms ผลดิบอยู่ใน docs/evidence/k6-delay-abort-eval.txt

ถ้าต้องการตัดสินเฉพาะช่วงภาวะคงตัวจริง ๆ

ต้องแยกข้อมูล ไม่ใช่เลื่อนเวลา มีสามวิธีที่ได้ผล

  1. แยกช่วงภาวะคงตัวเป็น scenario ของตัวเอง แล้วตั้ง threshold อ้างแท็ก scenario — k6 คิดเปอร์เซ็นไทล์จากเฉพาะตัวอย่างของ scenario นั้น (ตรวจแล้วว่าได้ผลจริง, exit code 0)
  2. รันช่วงภาวะคงตัวเป็นการรันแยกต่างหาก แล้วอ่านผลเฉพาะการรันนั้น
  3. ส่งออกข้อมูลดิบแล้วเลือกช่วงเวลาเอง ด้วย -o csv=raw.csv แล้วตัดช่วงอุ่นเครื่องออกก่อนคำนวณ
วิธีที่ 1 — แยก scenario แล้วตั้ง threshold อ้างแท็ก scenario 
export const options = {
  scenarios: {
    // ช่วงอุ่นเครื่อง: ไม่มีใครนำตัวเลขช่วงนี้ไปตัดสิน
    warmup: { executor: 'constant-vus', vus: 2, duration: '2m', exec: 'warmup', startTime: '0s' },
    // ช่วงภาวะคงตัว: เริ่มหลังช่วงอุ่นเครื่องจบ
    steady: { executor: 'constant-vus', vus: 10, duration: '10m', exec: 'steady', startTime: '2m' },
  },
  thresholds: {
    // อ้างแท็ก scenario เพื่อให้คิดจากเฉพาะตัวอย่างของ scenario นั้น
    'http_req_duration{scenario:steady}': ['p(95)<500', 'p(99)<1500'],
  },
};

export function warmup() { /* ยิงคำขอแบบเดียวกับ steady */ }
export function steady() { /* ยิงคำขอที่จะใช้ตัดสิน SLO */ }

การแยก scenario ทำให้ตัวเลขที่ใช้อ้างอิงสะอาดจริง ส่วน delayAbortEval ให้ผลแค่ "ไม่หยุดเร็วเกินไป" โดยตัวเลขที่รายงานยังรวมทุกอย่าง

ข้อมูลช่วงอุ่นเครื่องไม่ได้ถูกตัดออกให้

k6 นำทุกคำขอรวมช่วงอุ่นเครื่องไปคำนวณในสรุปท้ายการรัน ถ้าการรันสั้นมาก เช่น 30 วินาที ช่วงอุ่นเครื่องอาจกินไปครึ่งหนึ่งของทั้งหมด การรันที่ตั้งใจวัดผลจริงจึงควรยาวอย่างน้อย 5–10 นาที เพื่อให้ช่วงที่มีความหมายกินสัดส่วนมากพอ

think time กับ pacing ต่างกันอย่างไร

ทั้งสองอย่างทำให้รอบถัดไปเริ่มช้าลง แต่กลไกต่างกัน

เปรียบเทียบ think time และ pacing
ประเด็น think time (sleep) pacing
กลไก หยุดรอเป็นเวลาคงที่ทุกครั้ง คำนวณว่าเหลือเวลาอีกเท่าไรจากเป้าต่อรอบ แล้วรอเฉพาะส่วนที่เหลือ
เมื่อระบบตอบช้าลง รอบถัดไปเริ่มช้าลงตามระบบ รวม sleep เข้าไปอีก → รอบยาวขึ้นเรื่อย ๆ เวลารอหดลงเพื่อชดเชย ทำให้จังหวะต่อรอบคงที่
จำนวนคำขอต่อชั่วโมง แปรผันตามความเร็วของระบบ คงที่ตามที่กำหนด
เหมาะกับ การเลียนแบบพฤติกรรมผู้ใช้ที่อ่านหน้าจอ การทดสอบที่ต้องคุมจำนวนคำขอต่อชั่วโมงให้แน่นอน

think time คงที่ทำให้จำนวนคำขอต่อชั่วโมงแปรผันตามความเร็วของระบบ เป็นพฤติกรรมของแบบจำลองปิด

เลือกแบบจำลองให้ตรงกับความจริงที่ต้องเจอ

แบบจำลองปิดและแบบจำลองเปิด
ประเด็น แบบจำลองปิด (closed) แบบจำลองเปิด (open)
สิ่งที่ถูกตรึง จำนวนผู้ใช้ อัตราการเกิดงานต่อวินาที
executor constant-vus, ramping-vus, shared-iterations, per-vu-iterations constant-arrival-rate, ramping-arrival-rate
เมื่อระบบช้าลง ภาระที่ยิงเข้าลดลงเอง ภาระคงเดิม แล้วคิวจะยาวขึ้น หรือทิ้งงานถ้า VU ไม่พอ
สมจริงกับ ระบบปิด เช่นพนักงานในองค์กรที่แต่ละคนทำงานเป็นคิว ทราฟฟิกจากผู้ใช้ภายนอก ที่เข้ามาไม่สนใจว่าเราพร้อมไหม

สำหรับการยืนยันก่อนเปิดตัว แบบจำลองเปิดตอบได้ตรงกว่า เพราะทราฟฟิกจริงเข้ามาไม่หยุด ส่วนแบบจำลองปิดเหมาะกว่าเมื่อต้องเปรียบเทียบผลระหว่างการรันหลายครั้ง

จุดอิ่มตัว และวิธีหา

จุดอิ่มตัวคือจุดที่เพิ่มภาระต่อไปแล้ว throughput ไม่เพิ่ม แต่เวลาตอบสนองพุ่งขึ้น

วิธีหาแบบเพิ่มขึ้นทีละขั้น

เพิ่มจำนวนผู้ใช้เป็นขั้นละเท่า ๆ กัน ถือแต่ละขั้นนานพอที่ค่าจะนิ่ง แล้วเทียบ throughput กับเปอร์เซ็นไทล์

แบบฟอร์มบันทึกผลการทำ step test — ตัวอย่างวิธีกรอก ไม่ใช่ผลการวัด

เกณฑ์ตัดสินว่าถึงจุดอิ่มตัวมีสามข้อ ใช้ข้อใดข้อหนึ่งก็ได้ แต่ควรบันทึกทั้งสามไว้

  • เพิ่ม VUs อีก 100% แล้ว throughput โตไม่ถึง 20%
  • p95 โตเกิน 50% จากขั้นก่อนหน้า ขณะที่ throughput แทบไม่ขยับ
  • อัตราความผิดพลาดเริ่มสูงกว่าเกณฑ์ที่ยอมรับได้ ไม่ว่าจะเป็น 429, 503 หรือหมดเวลา

แถวแรกใช้ค่าจากการรันจริง (94/s กับ p95 75 ms) ขั้นที่เหลือเว้นเป็นคำถามโดยตั้งใจ เพราะต้องวัดจากระบบของคุณเอง

แปลง SLO เป็น threshold

SLO ที่เขียนให้วัดได้แปลงเป็น threshold ได้ตรงตัว ตารางนี้แสดงการแปลงที่พบบ่อย

แปลงข้อตกลงระดับบริการเป็นเงื่อนไขที่ k6 ตรวจได้
SLO ที่เขียนเป็นภาษา threshold ของ k6 metric ที่ใช้
ผู้ใช้ 95% ต้องรอไม่เกิน 300 มิลลิวินาที http_req_duration: ['p(95)<300'] http_req_duration (Trend)
ผู้ใช้ 99% ต้องรอไม่เกิน 1 วินาที http_req_duration: ['p(99)<1000'] http_req_duration (Trend)
คำขอที่ผิดพลาดต้องต่ำกว่า 1% http_req_failed: ['rate<0.01'] http_req_failed (Rate)
การตรวจผลทางธุรกิจต้องผ่านเกิน 99% checks: ['rate>0.99'] checks (Rate)
ต้องไม่มีรอบใดถูกทิ้งเพราะเครื่องทดสอบไม่พอ dropped_iterations: ['count<1'] dropped_iterations (Counter)
ข้อผิดพลาดที่พบบ่อยในการเขียน threshold
  • เขียน rate<1 แทน rate<0.01 เพราะ rate เป็นสัดส่วนทศนิยม ค่า 1 จึงหมายถึง 100% ซึ่งเท่ากับไม่มีเกณฑ์เลย
  • ใช้ avg แทน p(95) ทั้งที่ SLO เขียนด้วยเปอร์เซ็นไทล์
  • ใส่ช่องว่างในนิพจน์ เช่น 'p (95) < 500' ที่ถูกคือ 'p(95)<500' ไม่มีช่องว่างเลย
  • ลืมตั้ง threshold ให้ checks แล้วคิดว่าผลของ check จะทำให้การรันล้มเหลวเอง

ถ้าใช้ abortOnFail กับหลายเกณฑ์ ต้องคิดล่วงหน้าว่าจะหยุดเมื่อใด โดยทั่วไปให้ตั้ง abortOnFail: true เฉพาะเกณฑ์ที่หมายความว่า "ระบบกำลังพัง ไม่ต้องทดสอบต่อ" เช่นอัตราความผิดพลาดเกิน 5% ส่วนเกณฑ์ด้านประสิทธิภาพให้รายงานผลไปโดยไม่หยุด

throughput กับ latency และการเสื่อมสภาพอย่างค่อยเป็นค่อยไป

สองค่านี้ไม่ใช่ตัวชี้วัดเดียวกัน throughput สูงอาจมาพร้อม latency ที่แย่ และ latency ที่ดีอาจมาจากการยิงภาระน้อย

อ่านคู่ตัวเลข throughput กับ latency พร้อมกัน
throughput latency ตีความ ควรทำอะไร
สูง ต่ำ ภาวะที่ต้องการ — ระบบมีกำลังเหลือ เพิ่มภาระเพื่อหาว่าขีดจำกัดอยู่ตรงไหน
สูง สูง ยังทำ throughput ได้ แต่เริ่มแลกด้วยเวลาของผู้ใช้ หาสาเหตุที่ทำให้แต่ละคำขอช้า และตัดสินว่ายอมรับได้หรือไม่
ทรงตัว พุ่ง เลยจุดอิ่มตัวแล้ว งานส่วนเกินไปต่อคิว หยุดเพิ่ม VU กลับไปแก้คอขวดก่อน
ลดลง พุ่ง ระบบเริ่มเสียงาน อยู่ในช่วงพัง หยุดทดสอบ ตรวจว่าเกิดอะไรขึ้นกับระบบปลายทาง

graceful degradation คือคุณสมบัติที่ยอมให้บริการบางส่วนช้าลงหรือถูกปฏิเสธ เพื่อรักษาบริการส่วนอื่นไว้ ตัวอย่างที่พบบ่อยคือตอบ 429 พร้อมส่วนหัวบอกให้ลองใหม่ทีหลัง หากทดสอบ stress แล้วพบ 429 สม่ำเสมอ นั่นเป็นสัญญาณว่าระบบมีกลไกนี้อยู่จริง

เมื่อเครื่องทดสอบกลายเป็นคอขวดเอง

อันตรายที่สุดของการตีความผลผิดคือคิดว่ากำลังวัดขีดจำกัดของระบบ ทั้งที่จริงวัดขีดจำกัดของเครื่องที่รัน k6 สัญญาณเตือนมีสี่ข้อ

  • dropped_iterations มากกว่า 0 แปลว่า k6 ไม่มี VU ว่าง ให้เริ่มรอบตามกำหนด โหลดที่สร้างได้จึงต่ำกว่าแผน
  • CPU ของเครื่องที่รัน k6 แตะ 100% แปลว่าไม่เหลือกำลังสร้างภาระเพิ่ม
  • http_req_blocked สูงขึ้นตามจำนวน VU แปลว่า การรอ socket ฝั่งเครื่องทดสอบเป็นตัวจำกัด ไม่ใช่ฝั่งเซิร์ฟเวอร์
  • เพิ่ม VU แล้ว vus ที่ทำได้จริงไม่ถึงเป้า ให้สงสัยเพดาน connection ของเครื่องทดสอบ

วิธีแก้เรียงตามลำดับที่ควรลอง

  1. ลดอัตราเป้าหมายลงก่อน เพื่อยืนยันว่าโหลดที่ต้องการสร้างได้
  2. ย้ายการทดสอบไปเครื่องที่ไม่ได้ทำงานอื่นอยู่
  3. แยกเครื่องทดสอบหลายเครื่องและรวมผลเข้าที่เดียว
  4. ใช้ executor แบบ arrival-rate เพื่อดูว่า k6 ทิ้งงานไปกี่รอบ
