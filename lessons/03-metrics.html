แคตตาล็อก metric — อ่านให้ออกว่าเวลาหายไปไหน

k6 รายงาน sub-metric ที่แยกเวลาของคำขอออกเป็นส่วน ๆ จึงตอบได้ว่าปัญหาอยู่ที่ เซิร์ฟเวอร์ เครือข่าย หรือเครื่องทดสอบ

ใช้เวลาอ่านประมาณ 20 นาที
ต้องอ่านก่อน: บทที่ 1
อ่านคู่กับ: อภิธานศัพท์

ใจความสำคัญ

  1. metric มีสี่ชนิด Counter, Gauge, Rate, Trend และ Gauge อย่าง vus ห้ามบวกกัน ให้อ่านเป็น min/max/avg
  2. http_req_duration = sending + waiting + receiving ส่วน blocked, connecting และ tls_handshaking ถูกวัดแยกออกมานอก duration
  3. ในการรันนี้ waiting กิน 99.58% ของ duration คอขวดจึงอยู่ที่เซิร์ฟเวอร์
  4. ผลของ check ไม่ทำให้การรันล้มเหลวถ้าไม่มี threshold คุม และ expected_response ทำให้ http_req_failed ไม่เตือน 4xx

ย้อนดู: สี่คำที่ต้องจำ (VU · RPS · RT · Budget)

ข้อมูลชุดเดียวกับหน้าอภิธานศัพท์

คำอธิบาย metric ทุกตัวในหน้านี้ และคำศัพท์ในหน้า อภิธานศัพท์ อ่านมาจากไฟล์ข้อมูลไฟล์เดียวกันคือ assets/data/metrics.json จึงไม่มีทางที่คำอธิบายจะขัดกันเองระหว่างสองหน้า ถ้าแก้คำอธิบายที่ไฟล์นั้น ทั้งสองหน้าจะเปลี่ยนตามพร้อมกัน

ชนิดของ metric และสิ่งที่บอกได้

metric สี่ชนิดของ k6 และวิธีอ่านค่าที่ถูกต้อง
ชนิด ค่าที่เก็บ วิธีอ่านที่ถูก ตัวอย่าง
Counter ยอดสะสม เพิ่มอย่างเดียว ลดไม่ได้ อ่านผลรวม และดูอัตราต่อวินาทีที่ k6 คำนวณให้ http_reqs, iterations, data_sent, dropped_iterations
Gauge ค่าขณะใดขณะหนึ่ง ขึ้นลงได้ อ่านเป็น min/max/avg ของค่าที่วัดได้ ไม่ใช่ผลรวม vus, vus_max
Rate สัดส่วนของเหตุการณ์ที่เกิดขึ้น อ่านเป็นเปอร์เซ็นต์ โดยค่าอยู่ระหว่าง 0 กับ 1 http_req_failed, checks
Trend การกระจายของค่าที่วัดได้ อ่านเป็นชุดค่าสถิติ ต้องดูลึกกว่าแค่ค่าเฉลี่ย http_req_duration, iteration_duration, http_req_waiting
ข้อผิดพลาดที่พบบ่อยกับ Gauge

vus เป็น Gauge จึงไม่มีความหมายถ้าจะนำมาบวกกัน ในการรันของเรา k6 เก็บค่า vus ไว้ 12 ตัวอย่าง แต่ละตัวมีค่า 10 ผลรวมคือ 120 ซึ่งไม่มีความหมายอะไร ส่วนที่ควรอ่านคือ avg 10, min 10, max 10 ซึ่งยืนยันว่าจำนวน VU ที่ทำงานจริงตรงกับที่ตั้งไว้ในทุกระยะของการรัน

แคตตาล็อก metric ทั้งหมด

คอลัมน์ขวาสุดคือค่าที่วัดได้จากการรัน k6 v2.2.0 ด้วย 10 VUs เป็นเวลา 12 วินาที ช่องว่างคือ metric ที่ไม่ได้เก็บค่า

กำลังอ่านไฟล์ข้อมูล metric

เวลาของหนึ่งคำขอประกอบด้วยอะไร

ส่วนที่หนึ่ง — วัดแยก ไม่ถูกรวมใน http_req_duration http_req_blocked เวลารอ socket ว่างจาก pool http_req_connecting เวลาเปิด TCP connection ใหม่ http_req_tls_handshaking เวลาทำ TLS handshake ส่วนที่สอง — http_req_duration คือผลรวมของสามตัวนี้ http_req_sending เวลาเขียน request ลง socket http_req_waiting เวลารอไบต์แรกจากเซิร์ฟเวอร์ (TTFB) http_req_receiving เวลารับ response body ที่เหลือ
sending + waiting + receiving = http_req_duration 0.054 ms + 54.02 ms + 0.172 ms = 54.246 ms เทียบกับค่าเฉลี่ยที่ k6 รายงาน: 54.25 ms ตรงกัน เมื่อใช้ค่าทศนิยมเต็มจากการหารผลรวมด้วย 1,155 0.0541 + 54.0254 + 0.1723 = 54.2518 ms ผลรวมของทั้งสามตัว = 62,660.934 ms ผลรวมของ duration = 62,660.934 ms

บรรทัดสุดท้ายรวมค่าดิบทั้ง 1,155 ค่าแล้วเทียบกันตรง ๆ ยืนยันว่าความสัมพันธ์นี้เป็นจริงทุกคำขอ

แล้ว blocked, connecting, tls หายไปไหน

สามตัวนี้ไม่ได้หายไป แต่ถูกวัดแยกออกมา ถ้านำค่าเฉลี่ยมารวมด้วยจะได้ 0.0231 + 0.0097 + 0 = 0.0328 ms ซึ่งเป็นเวลาที่ใช้ไปก่อนเริ่มส่งคำขอจริง เวลารวมทั้งหมดที่เครื่องทดสอบมองเห็นจึงเป็น 54.25 + 0.03 = 54.28 ms ตัวเลข 0.0328 ms นี้ยังตรงกับผลต่างระหว่างผลรวมของทุก metric กับผลรวมของ duration พอดี

แยกให้ออก: ปัญหาอยู่ฝั่งไหน

สัดส่วนเวลาของแต่ละส่วน เทียบกับ http_req_duration 54.25 ms
metric avg (ms) สัดส่วน อยู่ใน duration หรือไม่ ถ้าค่านี้สูงผิดปกติ ให้ไปดูที่
http_req_waiting 54.0254 99.58% อยู่ใน โค้ดฝั่งเซิร์ฟเวอร์ ฐานข้อมูล หรือบริการที่ถูกเรียกต่อ — คอขวดอยู่ที่นี่
http_req_receiving 0.1723 0.32% อยู่ใน ขนาด response และการบีบอัดข้อมูล
http_req_sending 0.0541 0.10% อยู่ใน ขนาด request body และคุณภาพเครือข่ายขาออก
http_req_blocked 0.0231 0.04% ไม่อยู่ จำนวน connection ที่เครื่องรัน k6 มีให้ใช้ และเพดาน file descriptor
http_req_connecting 0.0097 0.02% ไม่อยู่ การปิด connection reuse โดยไม่จำเป็น หรือเครือข่ายที่คุณภาพต่ำ
http_req_tls_handshaking 0.0000 0.00% ไม่อยู่ การตั้งค่า TLS session resumption (การรันนี้ใช้ http จึงเป็น 0)

ในการรันนี้ waiting กินเวลา 99.58% ของเวลาทั้งหมด คอขวดอยู่ที่เซิร์ฟเวอร์ ไม่ใช่เครือข่ายหรือเครื่องทดสอบ

หลักคิดที่ใช้ได้ทุกครั้ง

ถ้า waiting คิดเป็นสัดส่วนมากสุด ปัญหาอยู่ที่เซิร์ฟเวอร์ — ถ้า blocked หรือ connecting สูง ปัญหาอยู่ที่เครื่องทดสอบหรือเครือข่าย — ถ้า receiving สูง ปัญหาอยู่ที่ขนาดข้อมูลที่ส่งกลับ ให้ดูสัดส่วนก่อนดูตัวเลขดิบ เพราะตัวเลข 54 ms ไม่ได้แปลว่าดีหรือแย่จนกว่าจะรู้ว่ามันไปอยู่ส่วนไหน

ทำไม blocked กับ connecting ถึงเป็น 0 เกือบทั้งหมด

ในการรันของเรา blocked มีค่า p95 เท่ากับ 0.02 ms และ connecting มี p95 เท่ากับ 0 เพราะคำขอส่วนใหญ่ใช้ connection เดิม เฉพาะชุดแรกของแต่ละ VU ที่เชื่อมต่อใหม่ ทั้งที่ค่าสูงสุดแตะ 2.82 ms และ 1.30 ms

ค่า max ที่สูงกว่า p95 มากเป็นธรรมชาติของ metric ที่เป็น 0 เกือบทั้งหมด คำขอที่เชื่อมต่อใหม่ไปโผล่ที่ max โดยไม่ขยับ p95 จึงต้องดูค่าเฉลี่ย เปอร์เซ็นไทล์ และค่าสูงสุดพร้อมกัน

metric ที่สร้างเอง

metric มาตรฐานของ k6 ไม่รู้จักโดเมนธุรกิจ ถ้าจะวัดเวลาที่ใช้ประมวลผลออร์เดอร์ หรือสัดส่วนการจองที่สำเร็จ ต้องสร้าง metric เอง

custom metric ทั้งสี่ชนิด 
import { Counter, Gauge, Rate, Trend } from 'k6/metrics';

// ตั้งชื่อให้บอกหน่วยและโดเมนของเรา เพื่อไม่ให้ชนกับ metric ของ k6
const ordersCompleted = new Counter('orders_completed_total');
const queueDepth      = new Gauge('worker_queue_depth');
const orderSuccess    = new Rate('order_success_rate');
const orderLatency    = new Trend('order_processing_time_ms', true); // true = แสดงเป็น ms

export default function () {
  const start = Date.now();
  const res = http.post(`${BASE_URL}/api/orders`, payload);

  orderLatency.add(Date.now() - start);
  orderSuccess.add(res.status === 201);
  if (res.status === 201) ordersCompleted.add(1);

  queueDepth.add(Number(res.headers['X-Queue-Depth'] || 0));
}

metric ที่สร้างซ้ำกับสิ่งที่มีอยู่ไม่ได้ข้อมูลเพิ่ม การสร้าง Trend มาวัดเวลาตอบสนอง ทั้งที่ http_req_duration มีอยู่แล้ว ทำให้ตารางผลลัพธ์ยาวขึ้น ให้สร้างเฉพาะ metric ที่มาตรฐานมองไม่เห็น

อ่านผลแบบต่าง ๆ

ทางออกของผลลัพธ์และสิ่งที่ได้จากแต่ละทาง
คำสั่ง ได้อะไร เหมาะกับ
k6 run script.js สรุปผลท้ายการรันแบบเต็ม ดูผลด้วยตาระหว่างพัฒนา
--summary-mode compact สรุปผลที่ตัดบรรทัดส่วนเกินและบรรทัด tag ออก ทำให้ตรวจอัตโนมัติเปรียบเทียบผลข้ามการรันได้ง่ายขึ้น
--summary-export=result.json ไฟล์ JSON ของสรุปผลท้ายการรัน เก็บประวัติและเทียบผลระหว่างการรันแต่ละครั้ง
-o json=out.json ข้อมูลดิบทุกจุดที่วัดได้ พร้อม tag ครบ วิเคราะห์เชิงลึกรายคำขอ เช่นการกระจายตัวของ latency
-o csv=out.csv ข้อมูลดิบในรูปแบบตาราง เปิดในสเปรดชีตได้ทันที ทำกราฟหรือคำนวณต่อเอง — ไฟล์หลักฐานของบทเรียนนี้ได้มาด้วยวิธีนี้
คำสั่งที่ใช้เก็บข้อมูลดิบไว้วิเคราะห์ต่อ 
# เก็บข้อมูลดิบรายคำขอออกเป็น CSV พร้อม tags ครบ
k6 run -o csv=raw.csv script.js

# เก็บสรุปผลท้ายการรันเป็น JSON เพื่อเทียบกับการรันครั้งก่อน
k6 run --summary-export=summary.json --summary-mode compact script.js

# เก็บทั้งสองแบบพร้อมกัน
k6 run -o csv=raw.csv --summary-export=summary.json script.js

แท็ก expected_response และกับดักของ 4xx

โดยค่าเริ่มต้น k6 ถือว่าสถานะ 4xx และ 5xx เป็นความล้มเหลว ทำให้ http_req_failed สูงขึ้น ซึ่งถูกต้องสำหรับ endpoint ที่ควรตอบ 200 แต่ผิดสำหรับ endpoint ที่ควรตอบ 404

บอก k6 ว่า 404 เป็นผลลัพธ์ที่คาดไว้ 
import { check } from 'k6';
import http from 'k6/http';

export default function () {
  const res = http.get(`${BASE_URL}/api/items/999999`, {
    tags: { expected_response: 'true' },  // 4xx ของคำขอนี้ไม่ถูกนับเป็นความล้มเหลว
  });

  // ยังต้องตรวจด้วย check เอง เพราะ http_req_failed จะไม่เตือนให้แล้ว
  check(res, {
    'สินค้าที่ไม่มีต้องตอบ 404': (r) => r.status === 404,
  });
}
ข้อควรระวัง

เมื่อตั้ง expected_response: 'true' แล้ว k6 จะไม่นับความล้มเหลวให้อีก ต้องเขียน check() ตรวจสถานะที่คาดไว้เองเสมอ ไม่อย่างนั้นการทดสอบที่ได้ผลลัพธ์ผิดทั้งหมดจะดูเหมือนผ่านไปได้ด้วยดี และควรตั้ง thresholds: { checks: ['rate>0.99'] } กำกับไว้ด้วย เพราะผลของ check ไม่ทำให้การรันล้มเหลวหากไม่มี threshold คุม

แท็กที่ k6 ใส่มาให้แล้ว

k6 ติดแท็กให้ทุกจุดข้อมูล จึงกรองและแยกดูภายหลังได้

แท็กมาตรฐานที่ติดมากับทุกจุดข้อมูลของ HTTP request
แท็ก ค่าที่เป็นไปได้ ประโยชน์
name URL หรือชื่อที่เราตั้งเอง จัดกลุ่ม URL ที่มีรหัสแตกต่างกันให้เป็นชื่อเดียว แล้วดูค่าเฉลี่ยรวมได้
status รหัสสถานะ HTTP แยกดู latency ของคำขอที่สำเร็จกับที่ล้มเหลว
method GET, POST และอื่น ๆ ดูว่าการเขียนข้อมูลช้ากว่าการอ่านแค่ไหน
scenario ชื่อ scenario ในสคริปต์ แยกผลเมื่อรันหลาย scenario พร้อมกัน
group ชื่อ group ที่ครอบอยู่ ดูเวลาของแต่ละขั้นตอนในสคริปต์แยกจากกัน
expected_response true หรือ false กรองเฉพาะคำขอที่ถูกนับเป็นความสำเร็จออกมาดู latency

สรุปบทที่ 3

  • metric มีสี่ชนิด Counter, Gauge, Rate, Trend ซึ่งอ่านค่าต่างกัน
  • http_req_duration = sending + waiting + receiving ตรวจกับผลรวมดิบทั้ง 1,155 ค่าแล้วได้ 62,660.934 ms เท่ากัน
  • blocked, connecting และ tls_handshaking ถูกวัดแยกออกมา รวมกันได้ 0.0328 ms
  • ดู http_req_failed คู่กับ http_reqs เพราะ throughput รวมคำขอที่ล้มเหลวไว้ด้วย
ลองเอง

เปิด หน้าสำรวจข้อมูล latency แล้วดูฮิสโตแกรมของ http_req_duration ทั้ง 1,155 ค่า จะเห็นว่าข้อมูลกระจุกตัวอยู่ในช่วงแคบ ๆ และมีหางยาวออกไปถึง 584 ms ซึ่งเป็นเรื่องที่ตัวเลขค่าเฉลี่ยบอกไม่ได้
