คำนวณ TPS / RPS ให้ตรงกับที่ k6 วัดได้

อัตราการประมวลผลของระบบเท่ากับจำนวนงานที่สำเร็จหารด้วยเวลาที่ใช้จริง และคำนวณล่วงหน้า จากจำนวน VU กับเวลาที่หนึ่งรอบใช้ไป ถ้าสองทางให้ค่าไม่ตรงกัน แปลว่ามีตัวแปรที่ถูกละไว้

ใช้เวลาอ่านประมาณ 18 นาที
ต้องอ่านก่อน: ไม่มี
ต้องมี: เครื่องคำนวณ

ใจความสำคัญ

  1. RPS นับคำขอ HTTP แต่ TPS นับธุรกรรมที่อาจกินหลายคำขอ สองค่าจึงเทียบกันไม่ได้ถ้าไม่รู้จำนวนคำขอต่อรอบ
  2. หนึ่งรอบของ VU ใช้เวลา (R × Rt) + Tt think time จึงกำหนด throughput พอ ๆ กับความเร็วเซิร์ฟเวอร์
  3. การแทน http_req_duration ในสูตรแทน iteration_duration ให้ค่าสูงเกินจริง 1.94 เท่า
  4. ตัวเลขที่คำนวณด้วยมือกับที่ k6 รายงานต่างกันเล็กน้อย เพราะสูตรสมมติว่า VU ทำงานเต็มเวลาเสมอ

ย้อนดู: สี่คำที่ต้องจำ (VU · RPS · RT · Budget)

TPS, RPS และ iterations/s ต่างกันอย่างไร

คำที่ใช้บ่อยและความหมายที่ตรงกับ metric ของ k6
คำ นับอะไร metric ที่ตรงกันใน k6 ใช้เมื่อไหร่
RPS จำนวนคำขอ HTTP ที่สำเร็จต่อวินาที http_reqs ใช้เป็นค่าเริ่มต้น เพราะตรงกับสิ่งที่ k6 รายงานตรง ๆ
TPS จำนวนธุรกรรมที่สำเร็จต่อวินาที โดยหนึ่งธุรกรรมอาจกินหลายคำขอ iterations เมื่อหนึ่งรอบเท่ากับหนึ่งธุรกรรม ใช้เมื่อคุยกับฝ่ายธุรกิจที่คิดเป็น "ออร์เดอร์ต่อวินาที" หรือ "การจองต่อนาที"
iterations/s จำนวนรอบของฟังก์ชัน default() ที่จบต่อวินาที iterations และ iteration_duration ใช้เป็นตัวกลางในการคำนวณ เพราะเป็นหน่วยที่ผูกกับ VU โดยตรง
เลือกคำให้ตรงกับงาน

ถ้าหนึ่งรอบยิงหนึ่งคำขอ คำทั้งสามให้ตัวเลขเดียวกัน แต่ถ้าหนึ่งรอบยิงห้าคำขอ ค่า RPS จะมากกว่า TPS ห้าเท่า รายงาน "ได้ 500 TPS" จึงต้องบอกจำนวนคำขอต่อรอบ

สูตรหลัก และการตรวจสอบกับผลที่ k6 รายงาน

TPS = จำนวน request ที่สำเร็จ ÷ เวลาที่ใช้จริง (วินาที)

การรันครั้งนี้ตั้งค่า 10 VUs 12 วินาที k6 รายงาน 1,155 คำขอ ใช้เวลารันจริง 12.36 วินาที มากกว่า 12 เพราะรอให้รอบสุดท้ายจบก่อนสรุปผล

TPS = 1,155 ÷ 12.36 = 93.45 request/s k6 รายงาน: http_reqs 1,155 93.44/s

สองค่าต่างกัน 0.01 request/s จากการปัดเศษของระยะเวลา 12.36 วินาที ให้ใช้ค่าที่ k6 รายงาน

หลักฐานจริง

การรัน k6 v2.2.0 ด้วย 10 VUs 12 วินาที ได้ 1,155 request ใช้เวลารันจริง 12.36 วินาที ดังนั้น 1,155 ÷ 12.36 = 93.45 request/s ขณะที่ k6 รายงาน http_reqs: 1,155 93.44/s ต่างกันไม่ถึง 0.02%

แบบจำลองปิด: หนึ่งรอบใช้เวลาเท่าไร

หนึ่งรอบของ default() มีสองก้อน: เวลารอคำตอบของทุกคำขอ และ think time ที่สั่งให้ VU หยุดรอด้วย sleep()

iteration_duration = (จำนวน request ต่อรอบ × เวลาตอบสนองเฉลี่ย) + think time iterations/s = จำนวน VU ÷ (iteration_duration เป็นวินาที) TPS = iterations/s × จำนวน request ต่อรอบ
N × R × 1000 TPS = ───────────────────── R × Rt + Tt N = จำนวน VU R = จำนวน request ต่อ 1 iteration Rt = เวลาตอบสนองเฉลี่ยต่อ request (มิลลิวินาที) Tt = think time ต่อ iteration (มิลลิวินาที)

หลักฐานที่สำคัญที่สุดในบทนี้

การรันของเราได้ iteration_duration เฉลี่ย 105.38 ms และ http_req_duration เฉลี่ย 54.25 ms สคริปต์มี sleep(0.05) หนึ่งจุด ส่วนต่าง 105.38 − 54.25 = 51.13 ms คือ think time 50 ms บวกค่าใช้จ่ายของสคริปต์

ใช้ iteration_duration (ถูกต้อง) 10 ÷ 0.10538 = 94.89 iterations/s → TPS = 94.89 × 1 = 94.89 request/s เทียบกับที่ k6 รายงาน 93.44/s ต่างกัน 1.5% ใช้ http_req_duration (ผิด) 10 ÷ 0.05425 = 184.33 iterations/s → สูงเกินจริง 1.94 เท่า

การใช้ http_req_duration แทน iteration_duration ให้ค่าสูงเกินจริง 1.94 เท่า เพราะเวลาครึ่งหนึ่งของ VU คือการนอนรอ

เวลาที่ VU ใช้จริงทั้งสิ้น 1,155 iterations × 105.3892 ms = 121,724.5 ms = 121.72 วินาที เวลานาฬิกาที่มีให้ใช้ 12.36 วินาที × 10 VUs = 123.60 วินาที สัดส่วนที่ VU ทำงานจริง 121.72 ÷ 123.60 = 0.985 หรือ 98.5% 94.89 × 0.985 = 93.45 iterations/s → ตรงกับ 93.44 ที่ k6 รายงาน

ที่ไม่ถึง 100% เพราะช่วงต้นและท้ายของการรัน VU บางตัวยังไม่เริ่มหรือหยุดไปแล้ว สูตรแบบง่ายจึงให้ค่าสูงกว่าความจริงเล็กน้อย

ตัวอย่างคำนวณทีละขั้น

ตัวอย่างที่ 1 — มี VU แต่ไม่มี think time

N = 10 VUs, R = 1, Rt = 100 ms, Tt = 0 ms

iteration_duration = (R × Rt) + Tt = (1 × 100) + 0 = 100 ms = 0.100 วินาที iterations/s = 10 ÷ 0.100 = 100 iterations/s TPS = 100 × 1 = 100 request/s

เคสนี้คือขอบเขตบนทางทฤษฎี เพราะ VU ยิงคำขอต่อเนื่องไม่หยุดพัก

ตัวอย่างที่ 2 — เพิ่ม think time เข้าไป

N = 10 VUs, R = 1, Rt = 100 ms, Tt = 200 ms

iteration_duration = (1 × 100) + 200 = 300 ms = 0.300 วินาที iterations/s = 10 ÷ 0.300 = 33.33 iterations/s TPS = 33.33 × 1 = 33.3 request/s

เทียบกับตัวอย่างที่ 1 think time 200 ms ทำให้ throughput ลดจาก 100 เหลือ 33.3 หรือหนึ่งในสาม ทั้งที่จำนวน VU และความเร็วเซิร์ฟเวอร์ไม่ได้เปลี่ยน

ตัวอย่างที่ 3 — หนึ่งรอบยิงหลายคำขอ

N = 10 VUs, R = 3 requests ต่อรอบ, Rt = 50 ms, Tt = 100 ms

iteration_duration = (3 × 50) + 100 = 250 ms = 0.250 วินาที iterations/s = 10 ÷ 0.250 = 40 iterations/s TPS = 40 × 3 = 120 request/s

ข้อสังเกตคือ iterations/s ลดลงเหลือ 40 จาก 100 ในตัวอย่างแรก แต่ TPS เพิ่มเป็น 120 เพราะแต่ละรอบยิงสามคำขอ การดูแค่ iterations/s โดยไม่รู้ค่า R จะสรุปว่าระบบช้าลง

คำนวณย้อนกลับ: ต้องใช้ VU เท่าไร

เป้าหมาย 500 request/s ต้องตั้ง VU เท่าไร หาได้โดยหารเป้าหมายด้วยกำลังผลิตของ VU แล้วปัดขึ้น

R × 1000 TPS ต่อ VU หนึ่งตัว = ───────────────── R × Rt + Tt จำนวน VU = ⌈TPS เป้าหมาย ÷ TPS ต่อ VU⌉

ตัวอย่าง — เป้าหมาย 500 request/s

R = 1, Rt = 50 ms, Tt = 150 ms

iteration_duration = (1 × 50) + 150 = 200 ms หนึ่งรอบใช้เวลา 0.2 วินาที TPS ต่อ VU = 1 × 1000 ÷ 200 = 5 request/s ต่อ VU จำนวน VU = ⌈500 ÷ 5⌉ = 100 VUs

ถ้าลืม think time 150 ms แล้วใช้แค่ Rt = 50 ms จะได้ 1,000 ÷ 50 = 20 request/s ต่อ VU แล้วสรุปว่าต้องใช้ ⌈500 ÷ 20⌉ = 25 VUs ซึ่งสร้างโหลดได้เพียง 125 request/s ขาดเป้าไป 75%

ตรวจสอบย้อนกลับกับข้อมูลจริง

สูตรนี้ใช้ได้กับผลที่วัดได้จริง แทนค่า Rt = 54.25 ms และ Tt = 50 ms จะได้ iteration_duration = 104.25 ms ใกล้เคียงกับ 105.38 ms ที่วัดได้ ส่วนต่าง 1.13 ms คือค่าใช้จ่ายของสคริปต์เอง

กฎของ Little: เชื่อม throughput เข้ากับจำนวนงานที่ลอยอยู่

กฎของ Little: จำนวนงานในระบบพร้อมกันเท่ากับอัตราที่งานไหลเข้าคูณเวลาที่งานแต่ละชิ้นใช้

N = อัตราการเกิดงาน × เวลาที่งานนั้นกินอยู่ ในหน่วยของเรา: N (จำนวนงานที่ลอยอยู่) = TPS × เวลาต่อรอบ (วินาที)
request ที่ลอยพร้อมกัน = TPS × Rt (วินาที) = 93.44 × 0.05425 = 5.07 request และถ้าดูที่ระดับรอบของ VU VU ที่ต้องใช้ = iterations/s × iteration_duration (วินาที) = 94.89 × 0.10538 = 10.0 VUs

จึงตั้ง 10 VU แต่มีคำขอลอยในระบบจริงเพียง 5.07 คำขอ เพราะอีกครึ่งหนึ่งของเวลา VU ทั้งสิบตัวนอนรอตามที่เราสั่งด้วย sleep() สัดส่วนเวลาที่ถูกจองโดยการรอคำตอบคือ 54.25 ÷ 105.38 = 51.5% ที่เหลือ 48.5% คือ think time

  • ใช้ได้กับค่าเฉลี่ยของเวลาต่อรอบ และเฉพาะช่วงที่ระบบคงตัว ไม่ใช่ช่วง ramp-up
  • ถ้าหนึ่งรอบยิงหลายคำขอพร้อมกัน ต้องนับคำขอที่ลอยพร้อมกันแยกจากจำนวน VU
  • กฎนี้บอกความสัมพันธ์ ไม่ได้บอกว่า VU เท่าไร "เพียงพอ" ขึ้นกับ latency ที่ยอมรับ
  • ถ้าคำนวณแล้วได้ VU ไม่ตรงกับที่ตั้งไว้ ให้ตรวจงานอื่นในรอบที่ไม่ได้นับ

ความสัมพันธ์ของ throughput, concurrency และ latency

throughput = concurrency ÷ latency จำนวนงานที่ทำได้ต่อวินาที = จำนวนงานที่ทำพร้อมกัน ÷ เวลาที่แต่ละงานใช้
เมื่อขยับตัวแปรหนึ่ง ตัวอื่นเปลี่ยนตามอย่างไร
สิ่งที่ทำ throughput latency ความหมายที่แท้จริง
เพิ่ม VU ในช่วงที่ระบบยังว่าง เพิ่มขึ้นเกือบเป็นสัดส่วน แทบไม่เปลี่ยน ยังมีกำลังเหลือ ยังไม่ถึงคอขวด
เพิ่ม VU หลังผ่านจุดอิ่มตัว ทรงตัวหรือลดลง พุ่งขึ้น กลายเป็นการต่อคิวให้ยาวขึ้น ไม่ได้ทำงานได้เร็วขึ้น
ทำให้แต่ละงานเร็วขึ้นเท่าตัว เพิ่มขึ้นเท่าตัวถ้ายังไม่ติดคอขวด ลดลง กำไรจริง แต่ต้องแก้ที่คอขวดที่ถูกตัว
เพิ่ม think time ลดลง เท่าเดิม ระบบไม่ได้ช้าลง แต่เราสร้างภาระน้อยลง

ข้อผิดพลาดที่พบบ่อย

  1. คำนวณจากค่าเฉลี่ยแล้วเทียบกับ SLO ที่เขียนด้วย p95 ถ้า SLO คือ p95 ต่ำกว่า 300 ms การนำค่าเฉลี่ยมาคำนวณ VU จะได้จำนวนน้อยเกินไป เพราะค่าเฉลี่ยต่ำกว่า p95 เสมอในระบบที่มีหาง ในการรันของเรา ค่าเฉลี่ย 54.25 ms แต่ p95 คือ 74.53 ms ต่างกัน 37%
  2. ลืม think time เป็นข้อผิดพลาดที่แพงที่สุด ตามที่คำนวณไว้ข้างต้นว่าทำให้ประเมิน VU ขาดไปถึง 75% ให้เปิดดู iteration_duration เพื่อยืนยันว่าค่าที่ใช้รวม think time แล้วจริง
  3. นับคำขอที่ล้มเหลวเป็น throughput http_reqs ของ k6 นับรวมคำขอที่ได้ 500 แม้ว่า http_req_failed จะรายงานว่าล้มเหลว ตัวเลข 93.44 request/s จึงต้องอ่านคู่กับ http_req_failed เสมอ ถ้าล้มเหลว 30% แปลว่ามีคำขอที่ได้ผลจริงเพียง 65 request/s
  4. รวมช่วง ramp-up และ warm-up เข้าไปคิด ช่วงต้นที่ VU ยังเพิ่มไม่ครบและระบบยังอุ่นไม่เสร็จ จะดึงค่าเฉลี่ยให้ต่ำกว่าความจริง วิธีที่ถูกคือคำนวณ throughput เฉพาะช่วง steady state เช่นแยกช่วงนั้นเป็น scenario ของตัวเองแล้ววัดจากแท็ก scenario หรือส่งออกข้อมูลดิบ แล้วเลือกช่วงเวลาเอง สังเกตว่า delayAbortEval ไม่ช่วยเรื่องนี้ เพราะมันเลื่อนแค่เวลาที่ k6 จะตัดสินใจหยุด ไม่ได้ตัดข้อมูลออกจากค่าเฉลี่ยที่รายงาน
  5. เข้าใจผิดว่า TPS คือความจุของระบบ ตัวเลขที่วัดได้เป็นผลรวมของหลายอย่างพร้อมกัน คือความเร็วของระบบปลายทาง ความเร็วของเครือข่าย ประสิทธิภาพของสคริปต์ และกำลังของเครื่องที่รัน k6 การเปลี่ยนเครื่องทดสอบจึงเปลี่ยนตัวเลขได้โดยที่ระบบปลายทางไม่ได้เปลี่ยนอะไรเลย
  6. เครื่องทดสอบเป็นคอขวดเองโดยไม่รู้ตัว ถ้าเห็น dropped_iterations มากกว่า 0 หรือ CPU ของเครื่องที่รัน k6 แตะ 100% แปลว่าเรากำลังวัดขีดจำกัดของเครื่องทดสอบ ไม่ใช่ของระบบ ให้ลดจำนวน VU ลงแล้วเพิ่มเครื่องทดสอบก่อนตีความผล
  7. ไม่ปิดหรือเปิด connection reuse อย่างตั้งใจ k6 ใช้ keep-alive โดยค่าเริ่มต้น ซึ่งทำให้ตัวเลขดีกว่าประสบการณ์ของผู้ใช้จริงที่เพิ่งเปิดเบราว์เซอร์ ควรทดลอง --no-connection-reuse เพื่อดูว่าผลต่างกันแค่ไหน ถ้าต่างกันมาก แปลว่าค่า handshake มีนัยสำคัญต่อ latency จริง
  8. นับ iterations เป็น TPS ทั้งที่หนึ่งรอบยิงหลายคำขอ ตามตัวอย่างที่ 3 ข้างต้น iterations/s 40 ไม่เท่ากับ TPS 120 ต้องคูณด้วยจำนวนคำขอต่อรอบเสมอ และควรระบุจำนวนนั้นไว้ในรายงานด้วย
  9. ใช้ระยะเวลาที่ตั้งใน stages แทนเวลาที่ใช้จริง ถ้าตั้ง duration: '12s' อย่าหารด้วย 12 ให้หารด้วยเวลาที่ k6 รายงาน เพราะมันมากกว่าเสมอตามที่เห็นว่า 12 วินาที กลายเป็น 12.36 วินาที

  • TPS = จำนวน request ที่สำเร็จ ÷ เวลาที่ใช้จริง (วินาที) ต้องตรวจกับค่าที่ k6 รายงานเสมอ

  • กฎของ Little: คำขอที่ลอยจริงมีเพียง 5.07 คำขอ จาก VU ทั้งหมด 10 ตัว
