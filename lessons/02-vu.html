virtual user คืออะไร และทำไมมันไม่ใช่เบราว์เซอร์จำลอง

VU ไม่ใช่เบราว์เซอร์ที่เปิดขึ้นมาทีละตัว แต่เป็นหน่วยทำงานที่ยิงคำขอ HTTP แล้วรอคำตอบ ความเข้าใจผิดนี้ทำให้ตั้งจำนวน VU น้อยกว่าที่ควร

ใช้เวลาอ่านประมาณ 16 นาที
ต้องอ่านก่อน: บทที่ 1
ตัวอย่างจริง: สคริปต์ 5 แบบ

ใจความสำคัญ

  1. VU มี default() ที่รันซ้ำเป็นลูป พร้อม JS runtime และ cookie jar ของตัวเอง ไม่ใช่เบราว์เซอร์จำลอง
  2. VU ถูกจองไว้ตลอดเวลาที่รอคำตอบ งานที่ลอยพร้อมกันจึงเท่ากับ throughput คูณ latency
  3. ตัวแปรในบริบท init อยู่ตลอดอายุ VU ส่วนตัวแปรใน default() เริ่มใหม่ทุกรอบ
  4. หลังจุดอิ่มตัว การเพิ่ม VU ทำให้เวลาต่อรอบยาวขึ้น แต่ throughput ไม่เพิ่ม

ย้อนดู: สี่คำที่ต้องจำ (VU · RPS · RT · Budget)

VU คือหน่วยทำงาน ไม่ใช่เบราว์เซอร์

k6 ที่ตั้ง 10 VU จะสร้างหน่วยทำงาน 10 หน่วย แต่ละหน่วยมี goroutine ของภาษา Go และ JavaScript runtime ของตัวเอง แล้วรัน default() ซ้ำเป็นลูป

ที่มา: ตารางนี้เปรียบเทียบเชิงคุณลักษณะของสองเครื่องมือ ตัวเลขช่วงในแถวสุดท้ายเป็นค่าประมาณเพื่อการวางแผน ค่าที่วัดได้จริงคือ vus: 10 และ vus_max: 10

VU วัดชั้น HTTP ไม่ได้วัดประสบการณ์ผู้ใช้จริง ถ้าหน้าจองตั๋วใช้ JavaScript ฝั่งเบราว์เซอร์ทำงานหนัก 1.5 วินาทีหลังได้ข้อมูลมา k6 จะไม่เห็นเวลานั้นเลย ต้องใช้ Playwright หรือ k6 browser module

VU ถูกจองไว้จนงานที่รับมาทำจนจบ ตัวเลขที่วัดได้จึงเป็นเวลาของชั้น HTTP ไม่ใช่เวลาที่ผู้ใช้รอ

วงจรชีวิตของ VU

  1. k6 อ่านและรันโค้ดระดับโมดูลหนึ่งครั้งต่อ VU ส่วนนี้เรียกว่าบริบท init ครอบคลุมทุกอย่างที่เขียนไว้นอกฟังก์ชัน รวมถึงการเรียกใช้ฟังก์ชันเพื่อเตรียมข้อมูล ตัวแปรที่สร้างตรงนี้จะเป็นของ VU ตัวนั้น
  2. VU เข้าสู่ฟังก์ชัน default() ซึ่งเป็นจุดที่ k6 ใช้เป็น "หนึ่งรอบการทำงาน" หนึ่งรอบอาจยิงคำขอเดียวหรือหลายคำขอ
  3. VU รอคำตอบ ในช่วงนี้ VU ถูกจองไว้ ทำงานอย่างอื่นไม่ได้เลย นี่คือหัวใจของคำอธิบายเรื่อง saturation ที่จะกล่าวถึงข้างล่าง
  4. VU ทำงานที่เหลือในรอบจนจบ เช่นการตรวจผลด้วย check() การเขียนค่าเข้า custom metric และการเรียก sleep() เพื่อให้ think time
  5. กลับไปเริ่มรอบใหม่ทันที ไม่มีการหยุดพักระหว่างรอบนอกจากที่เราสั่งไว้เอง แล้ววนซ้ำจนกว่าจะครบจำนวนรอบหรือหมดเวลาตามที่ executor กำหนด
state และ cookie แยกกันทุก VU

ตัวแปรที่สร้างใน default() จะเริ่มใหม่ทุกครั้งที่มีการรัน ไม่ค้างข้ามรอบ ส่วนตัวแปรที่สร้างในบริบท init จะอยู่ตลอดอายุของ VU นั้น และไม่ถูกแชร์ให้ VU อื่น เพราะแต่ละ VU มี JavaScript runtime ของตัวเอง cookies ก็เช่นกัน แต่ละ VU มี cookie jar ของตัวเอง จึงเลียนแบบผู้ใช้คนละคนได้ โดยไม่ต้องเขียนโค้ดจัดการอะไรเพิ่ม

เลือก executor ให้ตรงกับคำถาม

executor กำหนดว่า k6 สร้างภาระงานอย่างไร แบ่งเป็นสองตระกูล คือกำหนดจากจำนวนรอบ กับกำหนดจากอัตราการมาถึงของงาน

executor ที่ใช้บ่อยและความหมายที่แท้จริง
executor กำหนดอะไร พฤติกรรมเมื่อระบบช้าลง เหมาะกับ
shared-iterations โควตารวมของทุกรอบ โดยทุก VU แย่งกันทำ VU ที่เร็วทำมากกว่า จำนวนรอบรวมไม่เปลี่ยน งานที่ต้องแปรรูปข้อมูลเป็นชุด เช่นยิง 10,000 รายการให้จบ
per-vu-iterations แต่ละ VU ต้องทำครบตามจำนวนที่กำหนด รอบรวมเท่ากับ VU × จำนวนรอบเสมอ ต้องการให้ทุก VU ได้ทำงานเท่ากันจริง
constant-vus จำนวน VU คงที่ตามเวลา รอบต่อวินาทีลดลงเอง ตามแบบจำลองปิด ทดสอบที่ภาวะคงตัวและต้องการเทียบก่อน-หลัง
ramping-vus จำนวน VU เปลี่ยนตาม stages ที่กำหนด รอบต่อวินาทีลดลงเอง load, stress, spike, soak — รูปแบบที่ใช้บ่อยที่สุด
constant-arrival-rate จำนวนงานใหม่ต่อวินาที คงที่ อัตราคงเดิม แต่ต้องใช้ VU มากขึ้น หรือทิ้งรอบถ้า VU ไม่พอ เลียนแบบทราฟฟิกจากภายนอกที่ไม่สนใจว่าเราพร้อมไหม
ramping-arrival-rate อัตราการมาถึงของงานเปลี่ยนตาม stages เช่นเดียวกัน แต่ปรับอัตราได้ตามเวลา ทดสอบภาระสูงสุดที่คาดว่าจะเจอในอนาคต

ramping-vus เป็นแบบจำลองปิด จึงยิงช้าลงเองเมื่อระบบช้าลง ไม่ตรงกับทราฟฟิกภายนอก ที่ไม่สนใจว่าเราพร้อมไหม

VU ว่างงานตอนรอ และนั่นสำคัญมาก

ถ้าแต่ละคำขอใช้เวลา 100 ms และต้องการ 100 request/s ต้องมีงานลอยพร้อมกันอย่างน้อย 10 งาน หรือ VU 10 ตัวเมื่อไม่มี think time เพราะ VU ที่รอคำตอบถูกจองไว้กับงานนั้นจนจบ จึงเป็นไปตาม throughput = concurrency ÷ latency

จากบทที่ 1 — เทียบกับผลที่วัดได้จริง request ที่ลอยพร้อมกัน = 93.44 × 0.05425 = 5.07 VU ทั้งหมดที่ใช้ = 10 สัดส่วนเวลาที่ VU ถูกจองโดยการรอคำตอบ = 5.07 ÷ 10 = 50.7%

ตัวเลข 50.7% หมายความว่า VU ครึ่งหนึ่งกำลังนอนรอ think time ถ้าลด sleep() ลงครึ่งหนึ่ง throughput จะเพิ่มแต่ latency จะแย่ลง

think time ทำให้ TPS ต่อ VU ลดลงอย่างไร

VU กับ connection pool ไม่ใช่เรื่องเดียวกัน

จำนวน VU ไม่เท่ากับจำนวน connection ที่เปิดคู่กับเซิร์ฟเวอร์ k6 ใช้ keep-alive จึงนำ connection เดิมกลับมาใช้ซ้ำ

ตัวเลขที่ "ดีเกินจริง" เพราะ keep-alive

ผู้ใช้จริงที่เพิ่งเปิดเบราว์เซอร์ครั้งแรกต้องจ่ายค่าเชื่อมต่อเต็มจำนวน การทดสอบที่ใช้ connection ซ้ำจึงให้ตัวเลขที่ดีกว่าประสบการณ์ผู้ใช้กลุ่มนี้ ให้ลองรันด้วย --no-connection-reuse เพื่อดูว่าผลต่างกันเท่าไร ถ้าต่างกันมาก แปลว่าค่า handshake มีนัยสำคัญ และควรคำนึงถึงเมื่อวางแผนรับมือทราฟฟิกก้อนใหม่

เมื่อต้องยิงหลายคำขอพร้อมกันในหนึ่งรอบ ใช้ http.batch() ซึ่งยิงหลายรายการพร้อมกันจาก VU ตัวเดียว

ทำไมต้องค่อย ๆ เพิ่ม VU

  1. ระบบยังไม่อุ่นเครื่อง ช่วงต้นมีค่าใช้จ่ายจากการคอมไพล์โค้ด การเติม cache และการเปิด connection ซึ่งจะปนเข้าไปในผลถ้าเปิดเต็มที่ทันที
  2. เกิดภาระกระชากที่ไม่มีอยู่จริง VU 100 ตัวยิงคำขอแรกพร้อมกันในเสี้ยววินาทีเดียว สร้างคิวประดิษฐ์ที่บิดเบือนค่า p95 กับ p99
  3. หาไม่เจอว่าจุดอิ่มตัวอยู่ตรงไหน การไต่ขึ้นทีละขั้นทำให้เห็นว่าที่จำนวน VU เท่าไร throughput เริ่มหยุดโต ถ้าเปิดเต็มที่ทันทีจะรู้แค่ผลลัพธ์สุดท้าย

เพิ่ม VU แล้ว throughput ไม่เพิ่ม เพราะอะไร

กฎของ Little ในรูป throughput = concurrency ÷ latency ตอบคำถามนี้ เมื่อถึงจุดอิ่มตัว ทรัพยากรบางอย่างเต็ม เช่นเธรดของเว็บเซิร์ฟเวอร์ งานที่เพิ่มมาจึงต้องต่อคิว เวลาต่อรอบยาวขึ้นตามคิว

สัญญาณว่ากำลังอยู่ในภาวะอิ่มตัว

  • เพิ่ม VU แล้ว http_reqs ต่อวินาทีไม่ขยับ แต่ http_req_duration เพิ่มขึ้นเป็นสัดส่วน
  • http_req_waiting เพิ่มขึ้น ขณะที่ blocked และ connecting ยังเท่าเดิม → คอขวดอยู่ที่เซิร์ฟเวอร์
  • อัตราความผิดพลาดเริ่มสูงขึ้น โดยเฉพาะสถานะ 429 หรือ 503
  • dropped_iterations มากกว่า 0 → คอขวดอยู่ที่เครื่องทดสอบ ไม่ใช่ที่เซิร์ฟเวอร์

ต้นทุนของ VU หนึ่งตัว

VU เบากว่าเบราว์เซอร์มาก แต่ไม่ได้ฟรี หน่วยความจำต่อ VU ขึ้นกับข้อมูลที่โหลดไว้ใน init ถ้าอ่านไฟล์ทดสอบขนาด 50 MB เก็บในตัวแปรระดับโมดูล ทุก VU ถือสำเนาคนละชุด

ค่าประมาณเชิงขนานสำหรับวางแผน ไม่ใช่ผลการวัดในบทเรียนนี้
สิ่งที่เทียบ หน่วยความจำต่อหน่วย จำนวนที่เครื่องทั่วไปรับได้
VU ของ k6 (สคริปต์เบา) หลักร้อยกิโลไบต์ถึงหลักเมกะไบต์ หลักพันขึ้นไป
VU ของ k6 (โหลดข้อมูลก้อนใหญ่ใน init) บวกตามขนาดข้อมูลที่โหลดไว้ ลดลงตามขนาดข้อมูล
เบราว์เซอร์จริงหนึ่งหน้าต่าง หลักสิบถึงหลักร้อยเมกะไบต์ หลักสิบก่อนเครื่องเริ่มหน่วง
เธรดของระบบปฏิบัติการหนึ่งเธรด หลักเมกะไบต์ต่อสแตก หลักพัน

ที่มา: ตัวเลขในตารางนี้เป็นค่าประมาณเชิงขนาด ตัวเลขจริงขึ้นกับสคริปต์และเครื่อง การรันในบทเรียนนี้ใช้ VU เพียง 10 ตัว จึงไม่มีข้อมูล หน่วยความจำ ให้วัดจาก docker stats แทน

        { duration: '5m', target: 10 },  // steady state — ช่วงที่ข้อมูลมีความหมาย
        { duration: '3m', target: 10 },  // ถือภาวะเดิมต่อเพื่อดูว่าเสถียรไหม
        { duration: '1m', target: 0 },   // ผ่อนลง ให้คำขอที่ค้างอยู่ทำงานจนจบ
      ],
      gracefulRampDown: '30s',     // เวลาที่ให้รอบที่ค้างอยู่ทำจนเสร็จก่อนบังคับหยุด
    },
  },
  thresholds: {
    http_req_duration: ['p(95)<500'],  // p95 ไม่เกิน 500 ms
    http_req_failed: ['rate<0.01'],    // ความผิดพลาดต่ำกว่า 1%
  },
};

ตัวอย่างที่สองคือ constant-arrival-rate ต้องกำหนด maxVUs เสมอ

options แบบ constant-arrival-rate (open model) 
export const options = {
  scenarios: {
    steady_traffic: {
      executor: 'constant-arrival-rate',
      rate: 100,                   // ต้องเริ่ม 100 รอบใหม่ทุกวินาที
      timeUnit: '1s',              // หน่วยเวลาของ rate
      duration: '10m',             // ระยะเวลาที่จะสร้างภาระ
      preAllocatedVUs: 20,         // VU ที่จองไว้ล่วงหน้า
      maxVUs: 200,                 // เพดานที่ยอมให้ขยายได้ถ้างานค้าง
      // ถ้า maxVUs ไม่พอ k6 จะทิ้งรอบและนับใน dropped_iterations
      // ซึ่งแปลว่าโหลดที่สร้างได้จริงต่ำกว่าแผน ต้องแก้ก่อนตีความผล
    },
  },
  thresholds: {
    http_req_duration: ['p(95)<500'],
    http_req_failed: ['rate<0.01'],
    dropped_iterations: ['count<1'],   // ต้องไม่มีรอบใดถูกทิ้งเลย
  },
};

แบบจำลองเปิดใช้ http_req_duration เป็นเกณฑ์ได้ตรงกว่า เพราะอัตราการยิงถูกตรึงไว้ ส่วนแบบจำลองปิด ตัวเลข throughput กับ latency ขึ้นแก่กัน ต้องอ่านพร้อมกัน
