โหลดเทสต์คืออะไร และตอบคำถามอะไรให้เรา

โหลดเทสต์คือการสร้างภาระงานเทียมขึ้นมาชุดหนึ่ง แล้ววัดว่าระบบตอบสนองอย่างไร ภาระงานนั้นถูกกำหนดล่วงหน้าอย่างชัดเจนว่าใช้ผู้ใช้กี่คน นานเท่าไร และแต่ละคนทำอะไรบ้าง การทดสอบที่มีประโยชน์ต้องตอบคำถามได้ว่า "ที่ภาวะนี้ ระบบช้าลงเท่าไร" ไม่ใช่แค่ "ระบบรันผ่าน"

คำถามที่โหลดเทสต์ตอบได้ มีอยู่สี่กลุ่มหลัก

คำถามที่โหลดเทสต์ตอบได้ และตัวเลขที่ต้องดูเพื่อตอบคำถามนั้น
คำถาม ตัวเลขที่ต้องดู บทที่เกี่ยวข้อง
ตอนนี้ระบบทำได้กี่ request ต่อวินาที http_reqs, iterations, iteration_duration บทที่ 1
ผู้ใช้ส่วนใหญ่รอนานแค่ไหน และมีกี่คนที่รอนานผิดปกติ p95, p99 ของ http_req_duration และรูปร่างการกระจาย บทที่ 4
คอขวดอยู่ที่เซิร์ฟเวอร์ เครือข่าย หรือเครื่องทดสอบ สัดส่วนของ http_req_waiting เทียบกับ blocked และ connecting บทที่ 3
เพิ่มคนอีกเท่าตัวแล้วระบบยังไหวไหม จุดที่ throughput หยุดโตแล้ว latency เริ่มพุ่ง บทที่ 5
จริยธรรมและความปลอดภัย

โหลดเทสต์คือการยิงคำขอจำนวนมากด้วยความเร็วสูง ใส่ระบบของคนอื่นจึงไม่ต่างจากการโจมตี และอาจผิดกฎหมายได้ ตัวอย่างทุกตัวในบทเรียนนี้จึงชี้ไปที่ http://localhost:8080 ซึ่งเป็น mock server ที่แนบมากับโปรเจกต์นี้ หรือ https://test.k6.io ซึ่งเป็นโดเมนที่ผู้พัฒนา k6 สร้างขึ้นเพื่อการทดสอบโดยเฉพาะ ถ้าจะทดสอบระบบอื่น ต้องได้รับอนุญาตเป็นลายลักษณ์อักษรจากเจ้าของระบบก่อนเสมอ และควรใช้สภาพแวดล้อมทดสอบแทนระบบที่ผู้ใช้จริงใช้งานอยู่

k6 ทำงานอย่างไร

k6 เป็นโปรแกรมเดียวจบที่เขียนสคริปต์ด้วย JavaScript แล้วรันเป็นไบนารี ไม่ต้องติดตั้ง runtime อื่นเพิ่ม เพราะตัวรัน JavaScript ฝังอยู่ในไบนารีแล้ว เมื่อสั่ง k6 run จะเกิดลำดับดังนี้

  1. k6 อ่านค่าตั้งต้นจากฟังก์ชัน options ในสคริปต์ แล้วรู้ว่าต้องใช้ผู้ใช้เสมือนกี่ตัว นานเท่าไร และมีเกณฑ์ตัดสินอะไรบ้าง
  2. สร้าง virtual user (VU) ตามจำนวนที่กำหนด โดยแต่ละ VU มี runtime ของ JavaScript และหน่วยความจำของตัวเอง แยกจากกันโดยสมบูรณ์
  3. แต่ละ VU รันฟังก์ชัน default() ซ้ำเป็นลูป จนหมดเวลาหรือครบจำนวนรอบที่กำหนด ระหว่างที่รอ response จากเซิร์ฟเวอร์ VU นั้นว่างงาน ทำอย่างอื่นไม่ได้
  4. k6 รวมผลและเทียบกับ threshold แล้วสรุปออกมาเป็นตารางท้ายการรัน ถ้าเกณฑ์ข้อใดไม่ผ่าน จะจบด้วย exit code 99 ซึ่งทำให้ใช้กั้นในระบบอัตโนมัติได้ทันที

ประเด็นสำคัญที่ทำให้เข้าใจตัวเลขทั้งหมดในบทเรียนนี้คือ VU ไม่ใช่เบราว์เซอร์จำลอง มันไม่วาด HTML ไม่จัด CSS และไม่รัน JavaScript ของหน้าเว็บ หน้าที่ของมันมีอย่างเดียวคือยิงคำขอ HTTP แล้วรอคำตอบ ด้วยเหตุนี้ VU หนึ่งตัวจึงกินทรัพยากรน้อยมาก และการทดสอบจึงวัดได้แค่ชั้น HTTP ไม่ได้วัดเวลาที่เบราว์เซอร์ใช้เรนเดอร์หน้า

หลักฐานที่ใช้ตลอดบทเรียนนี้

ตัวเลขทุกตัวในบทเรียนนี้มาจากการรันครั้งเดียวกัน สคริปต์ยิงคำขอไปที่ mock server ในเครื่อง ด้วยผู้ใช้เสมือน 10 ตัว เป็นเวลา 12 วินาที ข้อมูลดิบถูกเก็บไว้ที่ docs/evidence/k6-csv-raw-sample.csv และ assets/data/latency-samples.json ซึ่งเป็นไฟล์ที่เว็บนี้อ่านไปวาดกราฟจริง ถ้าเห็นตัวเลขในบทเรียนที่ใด จะตรวจย้อนกลับได้จากสองไฟล์นี้เสมอ

เส้นทางการอ่าน

บทเรียนเรียงตามลำดับการใช้งานจริง คือเริ่มจากตัวเลขที่ต้องคำนวณเอง ไปจนถึงการอ่านผลลัพธ์ แต่ละบทต่อยอดจากบทก่อนหน้า ถ้ามีเวลาจำกัด ให้อ่านบทที่ 1 และ 4 ให้จบก่อน เพราะสองบทนี้เปลี่ยนวิธีที่เรามองตัวเลขประสิทธิภาพมากที่สุด

บทที่ 1

คำนวณ TPS / RPS

สูตร TPS จากจำนวน VU และเวลาต่อรอบ พร้อมตัวอย่างแทนค่าทีละขั้น และข้อผิดพลาดที่ทำให้ตัวเลขสูงเกินจริงสองเท่า

บทที่ 2

VU ทำงานอย่างไร

VU คืออะไร ถ้าไม่ใช่เบราว์เซอร์ ทำไมมันว่างงานตอนรอ response และทำไมเพิ่ม VU แล้ว throughput อาจไม่เพิ่ม

บทที่ 3

แคตตาล็อก metric

metric ทุกตัวที่ k6 รายงาน ชนิด หน่วย วิธีตีความ และวิธีแยกว่าปัญหาอยู่ฝั่งเซิร์ฟเวอร์หรือฝั่งเครือข่าย

บทที่ 4

เปอร์เซ็นไทล์ p95 / p99

คำนวณเปอร์เซ็นไทล์ด้วยมือทีละขั้น พร้อมกราฟจากข้อมูลจริง 1,155 ค่า ที่แสดงให้เห็นว่าค่าเฉลี่ยกลบหางอย่างไร

บทที่ 5

รูปแบบการทดสอบ

smoke, load, stress, spike, soak ต่างกันที่จุดประสงค์อย่างไร และแปลง SLO ให้เป็น threshold ได้อย่างไร

บทที่ 6

อ่านผลลัพธ์

ไล่ทีละบล็อกของสรุปผลท้ายการรัน และวิธีส่งออกผลไปทำกราฟต่อ รวมถึงปัญหาที่ทำให้อ่านผลผิด

ควรอ่านบทไหนเมื่อไหร่

เลือกบทตามสถานการณ์ที่กำลังเจออยู่
สถานการณ์ อ่านบท เหตุผล
เพิ่งรู้จัก k6 และยังไม่เคยรันสคริปต์เลย บทที่ 2 แล้วต่อ บทที่ 1 เข้าใจก่อนว่า VU ทำงานเป็นลูปอย่างไร สูตรในบทที่ 1 จึงจะไม่เป็นแค่การแทนตัวเลข
ต้องตอบหัวหน้าว่าระบบรับได้กี่ request ต่อวินาที บทที่ 1 มีสูตรและตัวอย่างการคำนวณย้อนกลับไปหาจำนวน VU ที่ต้องใช้
ผลการรันบอกว่าเร็ว แต่ผู้ใช้จริงยังบ่นว่าช้า บทที่ 4 อธิบายว่าทำไมค่าเฉลี่ยที่ดูดีจึงอยู่ร่วมกับประสบการณ์ที่แย่ได้
เห็นตัวเลขเต็มหน้าจอแต่ไม่รู้ว่าจะเริ่มอ่านตรงไหน บทที่ 3 และ บทที่ 6 บทที่ 3 ให้ความหมายของแต่ละบรรทัด บทที่ 6 สอนลำดับการอ่าน
ต้องออกแบบการทดสอบชุดใหม่สำหรับฟีเจอร์ที่กำลังจะเปิดตัว บทที่ 5 มีตารางเทียบรูปแบบการทดสอบและวิธีแปลง SLO เป็นเกณฑ์ที่วัดได้
threshold ไม่ผ่าน แต่ไม่แน่ใจว่าเป็นความผิดของระบบหรือของสคริปต์ แก้ปัญหาที่พบบ่อย แยกอาการ สาเหตุที่เป็นไปได้ และวิธีแก้ทีละกรณี
