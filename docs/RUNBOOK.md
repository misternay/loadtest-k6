# RUNBOOK.md — คู่มือปฏิบัติการ

คู่มือนี้ใช้ตอน **ดูแลและตรวจสอบ** เว็บไซต์บทเรียน loadtest-k6
ทุกคำสั่งในเอกสารนี้ถูก **รันจริงและผ่าน** แล้วเมื่อวันที่ 16 กันยายน 2026
บน k6 v2.2.0, Node v22.22.3, Chromium 153.0.8010.12 (macOS arm64)

> ทุกคำสั่งสมมติว่าเริ่มจากโฟลเดอร์ `loadtest-k6/`
> ถ้าอยู่ที่อื่นให้ `cd` เข้ามาก่อน

## 1. ตรวจสุขภาพเว็บไซต์ (ทำได้ทุกเมื่อ ไม่แก้อะไร)

ชุดนี้เป็น **read-only** ทั้งหมด ปลอดภัยที่จะรันบนเครื่องจริงหรือในไปป์ไลน์

### 1.1 ตรวจแบบเร็ว — ใช้เวลารวมไม่ถึง 2 นาที

```bash
cd loadtest-k6

echo "--- เวอร์ชันเครื่องมือ ---"
k6 version
node --version

echo "--- สูตรคำนวณและข้อมูล ---"
node scripts/test-calc.mjs; echo "test-calc exit=$?"

echo "--- คุณภาพเว็บไซต์ ---"
node scripts/verify-site.mjs; echo "verify-site exit=$?"
```

**เกณฑ์ผ่าน:**

| คำสั่ง | ต้องเห็น | exit code |
|---|---|---|
| `test-calc.mjs` | `เคสทั้งหมด 95 · ผ่าน 95 · ไม่ผ่าน 0` | `0` |
| `verify-site.mjs` | `ผลรวม: ตรวจ 50 รายการ · ผ่าน 50 · ไม่ผ่าน 0` | `0` |
| `word-count.mjs --check` | `ผลลัพธ์: การตัดสำนวนยังอยู่ในเกณฑ์ · โทเคนครบถ้วน` | `0` |

### 1.2 ตรวจแบบเต็ม — เพิ่มการเปิดด้วยเบราว์เซอร์จริง

```bash
node scripts/browser-check.mjs; echo "browser-check exit=$?"
```

**เกณฑ์ผ่าน:**

| `หน้าที่ไม่ใช่ 200` | `0` |
| `favicon ที่โหลดได้ 200` | `84 จาก 84 ครั้ง` |
| `คำขอ /favicon.ico` | `0 (ไม่มีเลย)` |
| `console error ทั้งหมด` | `0` |
| `page error ทั้งหมด` | `0` |
| `คำขอที่ล้มเหลว/4xx-5xx` | `0` |
| `หน้าที่มี overflow แนวนอน` | `0` |
| `จุดคอนทราสต์ที่ตรวจ` | มากกว่า 10,000 |
| `คอนทราสต์ที่ไม่ผ่าน` | `0` |

| บรรทัดสุดท้าย | `ผลลัพธ์: ผ่านทั้งหมด` |
| exit code | `0` |

### 1.3 ตรวจว่าปลายทางจำลองยังทำงาน

```bash
# สตาร์ท mock server ในเบื้องหลัง
node mock-server/server.mjs > /tmp/mock.log 2>&1 &
sleep 1

curl -s http://localhost:8080/health; echo
curl -s -o /dev/null -w "items = %{http_code}\n" http://localhost:8080/api/items
```

ต้องได้ `health = 200` และเห็น JSON ที่มี `"count":20`
บรรทัดสุขภาพต้องรายงาน `"tailRate":0` ด้วย ซึ่งหมายถึง mock server อยู่ใน
**โหมดประพฤติดี** (หางยาวปิด) — นี่คือโหมดที่ต้องใช้ก่อนรันชุดทดสอบทั้งหมด

ถ้าเห็น `"tailRate"` มากกว่า 0 แปลว่าสตาร์ทด้วย `TAIL_RATE=...` ซึ่งเป็นโหมดสาธิต
เปอร์เซ็นไทล์เท่านั้น **ห้ามใช้เป็นตัวกั้น smoke/load** ในโหมดนั้น ให้ปิดแล้วสตาร์ทใหม่:

```bash
pkill -f "mock-server/server.mjs"
node mock-server/server.mjs > /tmp/mock.log 2>&1 &
```

ถ้าต้องการสาธิตหางยาวเพื่อการสอน (บทที่ 4):

```bash
TAIL_RATE=0.03 node mock-server/server.mjs     # 3% ของคำขอช้าลง 150-570 ms
```

ปิดเมื่อเลิกใช้:

```bash
pkill -f "mock-server/server.mjs"
```

## 2. รันชุดทดสอบ k6

### 2.1 ลำดับที่ถูกต้อง

**ต้องสตาร์ท mock server ก่อนทุกครั้ง** ไม่งั้นสคริปต์จะได้ connection refused
และ `http_req_failed` จะเป็น 100%

```bash
cd loadtest-k6

# 1) สตาร์ทปลายทางจำลอง
node mock-server/server.mjs > /tmp/mock.log 2>&1 &
sleep 1

# 2) ตรวจว่าปลายทางพร้อม
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/api/items   # ต้องได้ 200

# 3) รันตามลำดับจากเบาไปหนัก — ห้ามข้าม smoke
k6 run k6/smoke.js
```

### 2.2 ระยะเวลาและน้ำหนักของแต่ละสคริปต์

เวลาที่ระบุคือเวลาที่ **วัดจากการรันจริงจนจบโปรไฟล์เต็ม** ในโปรเจกต์นี้
(ดู `docs/evidence/k6-load-full.txt` และ `k6-stress-full.txt`)

สำหรับ `spike.js` และ `soak.js` เวลาที่ระบุมาจากค่าที่ตั้งไว้ในไฟล์สคริปต์
**ยังไม่เคยรันจนจบในโปรเจกต์นี้** — ผู้ใช้สั่งข้ามเมื่อ 16 กันยายน 2026
เพราะใช้เวลานาน (ดู `HANDOFF.md` หัวข้อ 5.3)

| สคริปต์ | ระยะเวลา | VU สูงสุด | ควรใช้เมื่อ |
|---|---|---|---|
| `smoke.js` | 20 วินาที | 2 | ทุกครั้งก่อนอย่างอื่น |
| `load.js` | 12 นาที | `PEAK_VUS` (ค่าเริ่มต้น 10) | ยืนยันว่าที่ภาวะเป้าหมายยังผ่าน SLO |
| `stress.js` | 17 นาที | `BASE_VUS × 4` (ค่าเริ่มต้น 40) | หาจุดอิ่มตัว |
| `spike.js` | 9 นาที 10 วินาที | `SPIKE_VUS` (ค่าเริ่มต้น 50) | ดูการรับภาระกระชากและการฟื้นตัว |
| `soak.js` | `HOLD` + 4 นาที (ค่าเริ่มต้น 1 ชั่วโมง 4 นาที) | `VUS` (ค่าเริ่มต้น 10) | หาปัญหาระยะยาว |

เกณฑ์ของแต่ละสคริปต์ตั้งไว้ที่ระดับต่างกันโดยตั้งใจ

| สคริปต์ | เกณฑ์ | เหตุผล |
|---|---|---|
| `smoke.js` | `p(95)<1000`, `rate<0.01`, `checks>0.99` | เพดานสุขภาพ ไม่ใช่ SLO — smoke ตอบคำถามว่า "ทำงานไหม" |
| `load.js` | `p(95)<500`, `p(99)<1500`, `rate<0.01`, `checks>0.99` | เกณฑ์ SLO ที่ภาวะเป้าหมาย มี `abortOnFail` + `delayAbortEval 60s` |
| `stress.js` | `rate<0.05`, `p(95)<2000` | ผ่อนลงเพราะเจตนาไต่เลยภาวะปกติ มี `abortOnFail` + `delayAbortEval 90s` |
| `spike.js` | `rate<0.10`, `p(95)<3000` | ผ่อนมากเพราะเจตนาสร้างภาระกระชาก |
| `soak.js` | `p(95)<500`, `p(99)<1000`, `rate<0.01`, `checks>0.99` | เข้มเท่า load แต่ยาวนาน |

### 2.3 รันแบบย่อเมื่อไม่ต้องการรอเต็มโปรไฟล์

สคริปต์ทั้งห้าตั้ง `scenarios` กับ `stages` ไว้ในไฟล์เอง จึงตัด **เวลา** จากบรรทัดคำสั่ง
ได้ยาก สิ่งที่ทดลองแล้วกับ k6 v2.2.0:

| วิธี | ผลที่ได้จริง |
|---|---|
| `-d/--duration`, `-u/--vus`, `-i/--iterations`, `-s/--stage` | k6 พิมพ์เตือน `"cli" level configuration overrode scenarios configuration entirely` แล้วทับ scenario ทั้งก้อน กลายเป็นการรัน VU คงที่ ไม่มี ramp-up |
| `--execution-segment 0:33%` | **ไม่ได้ทำให้เวลาสั้นลง** — ลดภาระเหลือ 33% ของ VU แต่ยังรันจนครบเวลาเดิม<br>ทดลองกับสคริปต์ stages รวม 12 วินาที: ได้ `Up to 3 looping VUs for 12s` และ `running (11.9s)` ไม่ใช่ 4 วินาที |

วิธีที่ได้ผลคือลดจำนวน VU ผ่านตัวแปรสภาพแวดล้อมของสคริปต์ (ลดภาระ ไม่ได้ลดเวลา)
และลด `HOLD` ของ `soak.js` ซึ่งลดเวลาได้จริง:

```bash
# ลดภาระแต่ยังได้เห็น ramp-up ครบทุกช่วง (เวลายังเป็น 12 นาที)
k6 run -e PEAK_VUS=4 k6/load.js

# soak ลดเวลาได้จริงเพราะ HOLD กำหนดความยาวช่วงถือภาระ
k6 run -e VUS=2 -e HOLD=2m k6/soak.js      # ~6 นาที
```

ถ้าต้องให้ `load.js` / `stress.js` / `spike.js` สั้นจริง ๆ ต้องคัดลอกสคริปต์ไปแก้
`duration` ใน `stages` เอง **อย่าใช้ `--execution-segment` เพื่อหวังให้เวลาสั้นลง**

### 2.4 ความหมายของ exit code

ตารางนี้คัดลอกจากนิยามจริงในซอร์สโค้ดของ k6 (`errext/exitcodes/codes.go`)
ไม่ได้เดาจากพฤติกรรมที่สังเกต

| exit code | ชื่อในซอร์สโค้ด | หมายความว่า | ต้องทำอะไร |
|---|---|---|---|
| `0` | – | รันจบ และ threshold ผ่านทั้งหมด | – |
| `99` | `ThresholdsHaveFailed` | รันจบ แต่ **มี threshold ไม่ผ่าน** | อ่านบล็อก THRESHOLDS ว่าเกณฑ์ใดไม่ผ่าน แล้วดูว่าปัญหาอยู่ที่ระบบหรือที่เกณฑ์ **นี่คือ code ที่พบบ่อยที่สุดในโปรเจกต์นี้** |
| `100` | `SetupTimeout` | ฟังก์ชัน `setup()` ใช้เวลาเกิน timeout | ลดงานใน `setup()` |
| `101` | `TeardownTimeout` | ฟังก์ชัน `teardown()` ใช้เวลาเกิน timeout | ลดงานใน `teardown()` |
| `102` | `GenericTimeout` | หมดเวลาโดยไม่ระบุสาเหตุ | ตรวจ `maxDuration` และ `gracefulStop` |
| `103` | `ScriptStoppedFromRESTAPI` | ถูกสั่งหยุดผ่าน REST API ของ k6 | ตรวจว่าไม่มีสคริปต์อื่นสั่งหยุด |
| `104` | `InvalidConfig` | **ตั้งค่าผิด** สคริปต์หรือ CLI ไม่ถูกต้อง | อ่าน error บรรทัดแรก มักเป็นชื่อ option ผิดหรือค่าชนกัน |
| `105` | `ExternalAbort` | ถูกขัดจังหวะด้วยสัญญาณภายนอก (SIGINT, SIGTERM) เช่นกด Ctrl+C | รันใหม่ ไม่ควรนำผลมาเทียบ SLO |
| `106` | `CannotStartRESTAPI` | สตาร์ท REST API server ของ k6 ไม่ได้ | ตรวจว่าพอร์ต `--address` ว่าง |
| `107` | `ScriptException` | **สคริปต์โยน exception ระหว่างรัน** | อ่าน stack trace ที่ k6 พิมพ์ออกมา แก้ที่สคริปต์ |
| `108` | `ScriptAborted` | สคริปต์เรียก `test.abort()` เอง | เป็นการตั้งใจหยุด ตรวจว่าเงื่อนไขที่ทำให้ abort ถูกต้อง |
| `109` | `GoPanic` | k6 เองพัง (panic) | รายงานเป็นบั๊กของ k6 พร้อมแนบสคริปต์ที่ทำให้เกิด |
| `110` | `MarkedAsFailed` | สคริปต์เรียก `test.fail()` | ตรวจว่าเงื่อนไขที่ทำให้ fail ถูกต้อง |
| `97` / `98` | `CloudTestRunFailed` / `CloudFailedToGetProgress` | เกี่ยวกับ Grafana Cloud เท่านั้น | ไม่เกี่ยวข้องกับการรันในเครื่อง |

> **ข้อควรระวังที่พบจริงในโปรเจกต์นี้ (แก้แล้ว):** การใส่ตัวเลือกที่ k6 ไม่รู้จัก
> **ไม่ทำให้ exit code เปลี่ยน** k6 พิมพ์เพียงบรรทัดเตือน
> `level=warning msg="There were unknown fields in the options exported in the script"`
> แล้วเพิกเฉยต่อตัวเลือกนั้น การรันยังจบด้วย `0` หรือ `99` ตามปกติ
> **ดังนั้นอย่าใช้ exit code เป็นตัวบอกว่าตั้งค่าถูกต้อง**
>
> และมีกับดักซ้อนอีกชั้นที่พบจากการทดลอง: k6 ตรวจชื่อฟิลด์ที่ไม่รู้จัก
> **เฉพาะระดับบนสุดของ `options`** เท่านั้น ถ้าใส่ชื่อผิดไว้ *ข้างใน* ออบเจกต์
> รูปแบบยาวของ threshold (เช่นเคยใช้ `delayAbortedCheck` แทน `delayAbortEval`)
> k6 จะ **เงียบและเพิกเฉยโดยไม่มีบรรทัดเตือนเลย**
> วิธีตรวจที่เชื่อถือได้คือใช้ `k6 inspect` ซึ่งพิมพ์ตัวเลือกที่ k6 แปลงแล้วออกมา
> ให้ดูว่ามีคีย์ที่ต้องการอยู่จริงหรือไม่
>
> ```bash
> # ต้องไม่มีผลลัพธ์ใด ๆ ออกมา
> for f in smoke load stress spike soak; do k6 inspect k6/$f.js 2>&1 | grep -i 'unknown field'; done
> ```
>
> ดูหัวข้อ 5.4

แหล่งอ้างอิง: https://github.com/grafana/k6/blob/master/errext/exitcodes/codes.go

## 3. วิธีอ่านผลลัพธ์

### 3.1 ลำดับการอ่าน — อย่าอ่านตัวเลขก่อนตรวจว่าการรันสมบูรณ์

```
1) บรรทัด EXECUTION   →  running (…), N complete, M interrupted, vus, dropped_iterations
2) บล็อก THRESHOLDS   →  ผ่าน/ไม่ผ่าน และค่าจริงที่ใช้อ้างอิง
3) บล็อก checks       →  สัดส่วนการตรวจเงื่อนไขทางธุรกิจ
4) บล็อก HTTP         →  จำนวน อัตราความผิดพลาด เวลาตอบสนอง และ sub-metric
5) บล็อก NETWORK      →  data_received, data_sent
```

### 3.2 สัญญาณที่แปลว่าผลการรันใช้ไม่ได้

| เห็นอะไร | แปลว่า | ต้องทำ |
|---|---|---|
| `interrupted` มากกว่า 0 | มีรอบถูกตัดกลางทางตอนกด Ctrl+C หรือ abort | รันใหม่ ไม่ควรนำมาเทียบ SLO |
| `dropped_iterations` มากกว่า 0 | **เครื่องรัน k6 เป็นคอขวดเอง** ไม่ใช่ระบบปลายทาง | ลด VU ลง หรือเพิ่มเครื่องทดสอบก่อนตีความ |
| `vus max` ต่ำกว่าที่ตั้งใจ | k6 สร้าง VU ไม่ทันตอน ramp-up | ตรวจ CPU และหน่วยความจำของเครื่องทดสอบ |
| `data_sent` ใกล้ศูนย์ต่อคำขอ | ไม่ได้ส่ง body จริง | ตรวจว่าใช้ method และ payload ถูกตัว |
| `http_req_failed` สูงผิดปกติ แต่ปลายทางปกติ | 4xx ที่เป็นผลลัพธ์ที่คาดไว้ถูกนับเป็นความล้มเหลว | ใส่แท็ก `expected_response: 'true'` แล้วตรวจด้วย `check()` เอง |

### 3.3 อ่าน sub-metric เพื่อหาว่าคอขวดอยู่ที่ไหน

`http_req_duration = http_req_sending + http_req_waiting + http_req_receiving`

ให้ดู **สัดส่วน** ไม่ใช่ตัวเลขดิบ:

| ถ้าส่วนนี้กินเวลามากสุด | คอขวดอยู่ที่ |
|---|---|
| `http_req_waiting` | โค้ดฝั่งเซิร์ฟเวอร์ ฐานข้อมูล หรือบริการที่ถูกเรียกต่อ |
| `http_req_receiving` | ขนาด response และการบีบอัดข้อมูล |
| `http_req_sending` | ขนาด request body และคุณภาพเครือข่ายขาออก |
| `http_req_blocked` | จำนวน connection ใน pool ของเครื่องรัน k6 และเพดาน file descriptor |
| `http_req_connecting` | การปิด connection reuse หรือเครือข่ายคุณภาพต่ำ |

> `blocked`, `connecting` และ `tls_handshaking` **ไม่ถูกรวม** อยู่ใน `http_req_duration`
> ส่วน `sending`, `waiting`, `receiving` รวมกันเป็น `http_req_duration` พอดี

### 3.4 ดู p99 ที่ไม่ปรากฏบนหน้าจอ

k6 ไม่แสดง `p99` ให้โดยค่าเริ่มต้น มีสามทางเลือก:

```bash
# 1) เพิ่มสถิติที่แสดงในสรุปผล (ใช้ได้ทุกครั้ง ไม่ต้องแก้สคริปต์)
k6 run --summary-trend-stats="avg,min,med,max,p(90),p(95),p(99)" k6/smoke.js

# 2) ตั้ง threshold ที่อ้างถึง p99 แล้วค่าจะโผล่ในบล็อก THRESHOLDS
#    (แก้ในสคริปต์: http_req_duration: ['p(95)<500', 'p(99)<1500'])

# 3) ส่งออกข้อมูลดิบแล้วคำนวณเอง
k6 run -o csv=raw.csv k6/smoke.js
```

ความต่างของสามวิธีนี้

| วิธี | ได้อะไร | ใช้เมื่อ | ข้อจำกัด |
|---|---|---|---|
| `--summary-trend-stats` | เพิ่มบรรทัดสถิติบนจอสรุปท้ายการรัน | อยากเห็นเร็ว ๆ ไม่ต้องเก็บไฟล์ | เห็นเฉพาะค่าเดียวต่อ metric ไม่เห็นการกระจาย และไม่มีข้อมูลรายคำขอ |
| threshold ที่อ้าง p99 | ค่า p99 ในบล็อก THRESHOLDS พร้อมผลผ่าน/ไม่ผ่าน | ต้องการให้ไปป์ไลน์ตัดสินด้วย p99 | ต้องแก้สคริปต์ และใช้เป็นเกณฑ์ตัดสิน (ไม่ใช่แค่ดู) |
| `-o csv` / `-o json` | ข้อมูลรายคำขอทั้งหมด | ต้องคำนวณเปอร์เซ็นไทล์ช่วงเวลาที่เลือกเอง ทำฮิสโตแกรม หรือรวมหลายการรัน | ไฟล์ใหญ่ และต้องคำนวณเอง |

> `--summary-trend-stats` ต่างจาก `--summary-export` ตรงที่ตัวแรก **เปลี่ยนสิ่งที่พิมพ์บนหน้าจอ**
> ส่วน `--summary-export` **เขียนสรุปผลออกเป็นไฟล์ JSON** โดยไม่เปลี่ยนหน้าจอ
> ทั้งสองใช้ร่วมกันได้ และต่างจาก `-o csv/json` ซึ่งส่งข้อมูล **รายคำขอ** ออกไป
> ไม่ใช่สรุปผล (ดูตัวอย่างจริงใน `docs/evidence/k6-summary-trend-stats.txt`)

### 3.5 ทางออกของผลลัพธ์แบบต่าง ๆ

```bash
k6 run --summary-mode compact k6/smoke.js          # สรุปแบบสั้น อ่านบนหน้าจอ
k6 run --summary-mode full k6/smoke.js             # สรุปแบบเต็ม (ค่าเริ่มต้นคือ compact)
k6 run --summary-export=summary.json k6/smoke.js   # สรุปผลท้ายการรันเป็น JSON
k6 run -o csv=raw.csv k6/smoke.js                  # ข้อมูลดิบทุกจุด เปิดในสเปรดชีต
k6 run -o json=raw.json k6/smoke.js                # ข้อมูลดิบพร้อม tag ครบ

> **ตรวจความถูกต้องของตัวเลือกในสคริปต์เสมอ** อย่าดูแค่ exit code และอย่าดูแค่
> "มีบรรทัดเตือนไหม" เพราะ k6 ไม่เตือนเมื่อชื่อฟิลด์ผิดอยู่ข้างในออบเจกต์ threshold
>
> ```bash

> ```
>
> ถ้าไม่มีผลลัพธ์เลย แปลว่าไม่มีชื่อฟิลด์ที่ไม่รู้จัก ดูหัวข้อ 5.4

## 5. ปัญหาที่ทราบอยู่แล้ว (อย่าตกใจเมื่อเจอ)

### 5.1 ตัวเลข p94 / p9 ฯลฯ ไม่ปรากฏ

k6 แสดงเฉพาะสถิติที่ตั้งไว้ใน `--summary-trend-stats` ถ้าต้องการค่าอื่นให้เพิ่มเข้าไป
หรือส่งออกข้อมูลดิบแล้วคำนวณเอง

### 5.2 `vus` เป็น Gauge ห้ามนำมาบวกกัน

`vus` เก็บค่าชณะใดขณะหนึ่ง การนำผลรวมของ `vus` ไปใช้ไม่มีความหมาย
ให้อ่านเป็น `min` / `max` / `avg` เท่านั้น

### 5.3 `blocked` และ `connecting` อาจเป็น 0

ถ้าใช้ keep-alive (ค่าเริ่มต้น) คำขอส่วนใหญ่ใช้ connection เดิม
ค่าจึงเป็น 0 เกือบทั้งหมดและไปโผล่ที่ `max` แทน — เป็นเรื่องปกติ ไม่ใช่บั๊ก

### 5.4 ชื่อตัวเลือกของ threshold — `delayAbortEval` ไม่ใช่ `delayAbortedCheck`

**สถานะ: แก้แล้ว (16 กันยายน 2026)** — ทั้ง 13 จุดใน 9 ไฟล์เปลี่ยนมาใช้
`delayAbortEval` แล้ว และไม่มีบรรทัดเตือน `unknown field` เหลืออยู่

**อาการเดิม:** k6 v2.2.0 พิมพ์เตือน

```
level=warning msg="There were unknown fields in the options exported in the script"
  error="json: unknown field \"delayAbortedCheck\""
```

แล้ว **เพิกเฉยต่อตัวเลือกนั้นทั้งหมด** การรันยังจบปกติแต่ไม่มีผลอะไรตามที่ตั้งใจ

**ชื่อที่ถูกต้องคือ `delayAbortEval` วางในรูปแบบยาวของ threshold คู่กับ
`abortOnFail: true`:**

```javascript
thresholds: {
  http_req_duration: [{
    threshold: 'p(95)<500',
    abortOnFail: true,
    delayAbortEval: '60s',
  }],
}
```

**กับดักที่ต้องรู้ (พบจากการทดลอง 16 กันยายน 2026):**
k6 ตรวจชื่อฟิลด์ที่ไม่รู้จัก **เฉพาะระดับบนสุดของ `options`**
ถ้าใส่ชื่อผิดไว้ *ข้างใน* ออบเจกต์ threshold k6 จะ **เงียบสนิท ไม่มีบรรทัดเตือน**
กรณีเดิมเป็นเช่นนี้ทั้งสองแบบ: `load.js` วางไว้ระดับบนสุดจึงมีเตือน
ส่วน `stress.js` วางไว้ในออบเจกต์ threshold จึงเงียบ
**อย่าใช้ "มีบรรทัดเตือนไหม" เป็นวิธีตรวจ** ให้ใช้ `k6 inspect` ซึ่งพิมพ์
ตัวเลือกที่ k6 แปลงแล้วออกมา:

```bash
# ต้องไม่มีผลลัพธ์ใด ๆ ออกมา
for f in smoke load stress spike soak; do k6 inspect k6/$f.js 2>&1 | grep -i 'unknown field'; done
```

ยืนยันความไวของวิธีนี้: สคริปต์ที่ยังใช้ชื่อเก่าจะถูกจับได้ทันที
(ดู `docs/evidence/k6-delay-abort-eval.txt` ข้อ 1.1)

**พฤติกรรมจริงของ `delayAbortEval` — ยืนยันด้วยการรันจริง:**

| ทำ | ไม่ทำ |
|---|---|
| เลื่อน **เวลาที่ k6 จะตัดสินใจหยุดการรัน** เมื่อ threshold ที่ตั้ง `abortOnFail: true` ไม่ผ่าน | **ไม่ได้ตัดข้อมูลช่วงอุ่นเครื่องออกจากการคำนวณ threshold** — ค่าเปอร์เซ็นไทล์ที่ k6 รายงานท้ายการรันยังคิดจากทุกตัวอย่างรวมช่วงอุ่นเครื่อง |

หลักฐาน: `docs/evidence/k6-delay-abort-eval.txt`

- ไม่มี `delayAbortEval` → ถูกตัดจบเมื่อรันได้ 2.0 วินาที · มี `delayAbortEval '12s'` → ถูกตัดจบเมื่อรันได้ 12.0 วินาที
- ไม่มี `delayAbortEval` → รันจนจบ 20.1 วินาที รายงาน `p(95)=603.32 ms` · มี `delayAbortEval` → รันจนจบ 20.1 วินาที รายงาน `p(95)=602.49 ms` **เท่ากันในทางปฏิบัติ** ทั้งที่ 10 วินาทีแรกของทั้งสองรันถูกทำให้ตอบช้า 600 ms

**ถ้าต้องการตัดสินเฉพาะช่วงภาวะคงตัวจริง ๆ** (`delayAbortEval` ไม่ใช่เครื่องมือสำหรับเรื่องนี้)
มีสามวิธีที่ได้ผล ดูรายละเอียดในบทที่ 5 หัวข้อ "ถ้าต้องการตัดสินเฉพาะช่วงภาวะคงตัวจริง ๆ"
และตัวอย่างที่รันแล้วผ่านใน `docs/evidence/k6-delay-abort-eval.txt` ส่วนที่ 3:

```bash
# แยกช่วงภาวะคงตัวเป็น scenario ของตัวเอง แล้วตั้ง threshold แบบอ้างแท็ก scenario
k6 run docs/evidence/probes/probe-scenario-scope.js
```

### 5.5 `smoke.js` ไม่ผ่านเป็นครั้งคราว (exit 99) ทั้งที่ระบบปกติ

**สถานะ: แก้แล้ว (16 กันยายน 2026)** — รันซ้ำ 30 ครั้งติดกันผ่านทั้งหมด 30/30

**อาการเดิม:** รัน `k6 run k6/smoke.js` แล้วได้ exit 99 โดยที่ mock server ยังตอบ 200 ปกติ
ครั้งที่ไม่ผ่านมี `http_req_duration max` เกิน 500 ms (พบค่าสูงสุด 604.48 ms)
วัดได้ **37 ครั้ง ไม่ผ่าน 6 ครั้ง (~16%)**

**สาเหตุ (สองข้อประกอบกัน):**

1. `smoke.js` เดิมตั้ง `vus: 1, duration: '10s'` และมี `sleep(1)` จึงเก็บได้เพียง
   ราว 10 รอบ = 30 ข้อตรวจ เมื่อมีคำขอใดคำขอหนึ่งเกิน 500 ms จะทำให้
   check "ตอบภายใน 500 ms" ตกไป 1 ข้อ → `checks` = 29/30 = 96.7% ต่ำกว่าเกณฑ์ 99%
   จำนวนตัวอย่างน้อยขนาดนี้ยังทำให้ `p(95)` แทบไม่ใช่สถิติ
2. mock server เดิมเปิด **หางยาว 3%** (+150–570 ms) เป็นค่าเริ่มต้นตลอดเวลา
   ทำให้คำขอตกหางเป็นครั้งคราวโดยไม่มีอะไรผิด

**วิธีแก้ที่ใช้:**

| ฝั่ง | แก้เป็น | เหตุผล |
|---|---|---|
| `mock-server/server.mjs` | หางยาวปิดเป็นค่าเริ่มต้น เปิดด้วย `TAIL_RATE` เมื่อต้องการสาธิต | mock server ต้อง "ประพฤติดี" จึงใช้เป็นปลายทางอ้างอิงได้ |
| `k6/smoke.js` | `vus: 2, duration: '20s'` (~40 รอบ = 120 ข้อตรวจ) | ทำให้ `p(95)` และ `checks` rate มีความหมาย |
| `k6/smoke.js` | เกณฑ์เป็นเพดานสุขภาพ `p(95)<1000` ไม่ใช่ SLO 500 ms | smoke ตอบคำถามว่า "ทำงานไหม" ไม่ใช่ "ผ่าน SLO ไหม" |

**หลักฐาน:** `docs/evidence/k6-smoke-repeatability.txt` (30/30, exit 0 ทุกครั้ง)
และ `docs/evidence/k6-smoke.txt` (ผลเดิมก่อนแก้ 37 ครั้ง ไม่ผ่าน 6 ครั้ง)

**ผลกระทบต่อไปป์ไลน์:** ตอนนี้ใช้ `k6 run k6/smoke.js` เป็นตัวกั้นใน CI ได้
โดยมีเงื่อนไขว่า mock server ต้องรันในโหมดค่าเริ่มต้น (หางยาวปิด)
ถ้าปลายทางที่ใช้เป็นตัวกั้นมีหางยาวจริง ให้ผ่อนเกณฑ์ของ smoke ให้สะท้อนพฤติกรรมจริง
แล้วเก็บเกณฑ์ SLO ที่เข้มไว้ใน `load.js`

**ถ้า smoke ยังไม่ผ่านทั้งที่ mock server โหมดปกติ:** ให้ดูค่าก่อนสรุปว่ามีปัญหาจริง

```bash
k6 run k6/smoke.js 2>&1 | sed -n '/THRESHOLDS/,/checks/p'
```

| สิ่งที่เห็น | แปลว่า | ทำอะไร |
|---|---|---|
| `med` และ `p(95)` ต่ำกว่า 50 ms แต่ `max` สูงกว่าปกติมาก | มีคำขอเดียวสะดุด อาจเป็น GC หรือ scheduling ของเครื่อง | รันซ้ำหนึ่งครั้ง ถ้าผ่านถือว่าใช้ได้ |
| `med` สูงขึ้นด้วย หรือ `p(95)` เกิน 1000 ms | ระบบปลายทางหรือเครื่องทดสอบช้าจริง | ตรวจ `/health` และ CPU ของเครื่อง |
| `http_req_failed` ไม่ใช่ 0% | ปลายทางไม่ได้ตอบ 200 | ตรวจว่า mock server ยังทำงานและ `TARGET_PATH` ถูกต้อง |

## 6. ซ้อม rollback 1 รอบ

การซ้อมนี้ **ทำจริงและผ่านแล้ว** เมื่อวันที่ 16 กันยายน 2026 (ดูผลดิบใน
`docs/evidence/rollback-drill.txt`) ใช้เวลาไม่ถึง 3 นาที
**แนะนำให้ซ้อมซ้ำทุกครั้งก่อนอัปเดตบทเรียนครั้งใหญ่**

การซ้อมใช้สำเนาชั่วคราวใน `/tmp` จึงไม่แตะไฟล์จริง และไม่แตะ `assets/data/`

### ขั้นที่ 1 — เก็บสำเนาและค่า hash

```bash
cd loadtest-k6
STAMP=$(date +%Y%m%d-%H%M%S)
rm -rf /tmp/ltk6-drill && mkdir -p /tmp/ltk6-drill
cp -a site /tmp/ltk6-drill/site-$STAMP
( cd /tmp/ltk6-drill/site-$STAMP && find . -type f | sort | xargs shasum ) > /tmp/ltk6-drill/site-$STAMP.sha256
echo "$STAMP" > /tmp/ltk6-drill/STAMP
wc -l < /tmp/ltk6-drill/site-$STAMP.sha256      # ต้องได้ 28
```

### ขั้นที่ 2 — ตรวจว่าสำเนาครบถ้วน

```bash
STAMP=$(cat /tmp/ltk6-drill/STAMP)
( cd /tmp/ltk6-drill/site-$STAMP && find . -type f | sort | xargs shasum ) \
  | diff - /tmp/ltk6-drill/site-$STAMP.sha256 \
  && echo "สำเนาครบถ้วน" || echo "สำเนาไม่ครบ"
```

### ขั้นที่ 3 — จงใจสร้างความเสียหาย

จำลองเหตุการณ์จริงที่พบบ่อยที่สุด: favicon หายและพาธผิด

```bash
sed -i '' 's|href="favicon.svg"|href="favicon-broken.svg"|' site/index.html site/quiz.html
rm -f site/favicon.svg && ln -sf /nonexistent site/favicon.svg
```

### ขั้นที่ 4 — ยืนยันว่าตัวตรวจจับได้ (ขั้นนี้สำคัญที่สุด)

```bash
node scripts/verify-site.mjs   > /tmp/drill-v.txt 2>&1; echo "verify-site exit=$?"
node scripts/browser-check.mjs > /tmp/drill-b.txt 2>&1; echo "browser-check exit=$?"
grep "ผลรวม"   /tmp/drill-v.txt
grep "ผลลัพธ์" /tmp/drill-b.txt
```

**ต้องได้** `verify-site exit=1` และ `browser-check exit=1`
พร้อม `ผลรวม: ตรวจ 50 รายการ · ผ่าน 47 · ไม่ผ่าน 3`
(ตัวเลข 3 รายการที่พังคือ favicon ที่หายไป 2 จุด และการประกาศ favicon ผิดพาธอีก 1 จุด)

> ถ้าขั้นนี้ตัวตรวจ **ยังผ่าน** แปลว่าตัวตรวจใช้ไม่ได้ ให้หยุดและแก้ตัวตรวจก่อน
> การซ้อม rollback ที่ตัวตรวจไม่จับความเสียหายไม่มีความหมาย

### ขั้นที่ 5 — ย้อนกลับจากสำเนา

### ขั้นที่ 6 — ยืนยันว่าไฟล์กลับมาตรงกับสำเนาทุกไบต์
