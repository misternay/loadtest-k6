3) ผลทดสอบสไลเดอร์คู่กับช่องกรอก (browser-check ส่วนที่ 7)
================================================================================

  ตรวจ 2 ธีม × ธีมละ 25 ข้อ = ผ่านทั้งหมด 50 ข้อ

  สิ่งที่ทดสอบด้วยการโต้ตอบจริง:
    - ลากเมาส์บนรางจริง (mousedown → move 12 steps → mouseup)
      → ค่าสไลเดอร์เพิ่มขึ้น · ช่องกรอกเปลี่ยนตาม · aria-valuetext = "N VU"
      → ผลลัพธ์ใน #tps-output คำนวณใหม่จริง (พบ "N ÷ (" ในขั้นที่ 2 ของวิธีคิด)
    - พิมพ์ 250 ลงช่องกรอก → สไลเดอร์ขยับเป็น 250 และ aria-valuetext เป็น "250 VU"
    - พิมพ์ 900 (เกินเพดานสไลเดอร์ 500) → ค่าที่พิมพ์ไม่ถูกแก้ และสไลเดอร์ไม่หนีบ
      (ยังอยู่ที่ 250) — พิสูจน์ว่าสไลเดอร์ไม่เขียนทับค่าที่ผู้ใช้พิมพ์
    - พิมพ์ 0 ใน Rt และ -5 ใน Tt → ข้อความเตือนยังขึ้นเหมือนเดิม
      (#err-tps-Rt / #err-tps-Tt ไม่ hidden, aria-invalid="true") และสไลเดอร์ไม่ขยับ
    - คีย์บอร์ด: ArrowRight เลื่อนขึ้น 1 step และช่องกรอกตรงกัน · End ไปขอบขวา (20)
    - ปุ่ม "ใส่ค่าจากการรันจริง" ดึงสไลเดอร์ Rt กลับมาที่ 54.25 และ aria-valuetext
      เป็น "54.25 มิลลิวินาที"
    - ปุ่ม "ล้างค่า" ดึงสไลเดอร์กลับมาที่ค่าตั้งต้น 10 ตรงกับช่องกรอก

9) สิ่งที่ยังไม่ได้ทำ / ยังไม่ยืนยัน
================================================================================

  - ตรวจด้วย Chromium 153.0.8010.12 เท่านั้น ยังไม่ได้ทดสอบ Safari และ Firefox
    สไตล์สไลเดอร์มีทั้ง ::-webkit-slider-* และ ::-moz-range-* แต่ยังไม่ยืนยันบน
    เบราว์เซอร์จริง (โครงการนี้มีข้อจำกัดว่าทดสอบได้เฉพาะ Chromium ที่ติดตั้งไว้)
  - Chromium ปัดค่า range ที่ตั้งด้วยโปรแกรมให้ตรงกับ step: กรณีพิมพ์ค่าเป็น
    ทศนิยมลงช่องที่เป็นจำนวนเต็ม (เช่น 10.5 ในช่อง VU) สไลเดอร์จะปัดเป็น 11
    ขณะที่ช่องกรอกยังเป็น 10.5 และแสดงข้อความเตือน "ต้องเป็นจำนวนเต็ม" ตามเดิม
    เป็นพฤติกรรมที่ตั้งใจ (ช่องกรอกเป็นตัวจริง สไลเดอร์เป็นการสำรวจ) แต่ยังไม่ได้
    ทดสอบบนเบราว์เซอร์อื่น
  - ยังไม่ได้ทดสอบด้วยโปรแกรมอ่านหน้าจอจริง (NVDA/VoiceOver) — ตรวจเฉพาะ
    โครงสร้างที่อ่านออกเสียงได้ (label ผูกครบ, aria-valuetext, role="progressbar",
    aria-live) ตามหลักเกณฑ์
  - ยังไม่ได้วัดประสิทธิภาพการวาดหน้าเมื่อสไลเดอร์เปลี่ยนค่าแบบลากต่อเนื่อง
    (คำนวณใหม่ทุก event ซึ่งฟอร์มทำอยู่แล้วก่อนรอบนี้)
  - k6/ และ mock-server/ ไม่ถูกแตะและไม่ได้รันซ้ำในรอบนี้ (ไม่มีการเปลี่ยนสคริปต์)
  - คอนทราสต์ของหัวเลื่อนสไลเดอร์วัดจากค่าโทเคนที่เบราว์เซอร์ resolve แล้ว
    ไม่ได้สุ่มพิกเซล (เหตุผลในหัวข้อ 6)


10) ข้อผิดพลาดที่พบในงานของตัวเอง แล้วแก้ระหว่างรอบ (สำคัญ)
================================================================================

  ฉบับร่างแรกของส่วน "สี่คำที่ต้องจำ" (index.html) เขียนว่า

      "ที่ Rt 54.25 ms และ think time 50 ms หนึ่ง VU ยิงได้เพียง 9.49 คำขอต่อวินาที"

  ซึ่ง **ไม่ถูกต้อง** เมื่อเทียบกับตาราง "กำลังผลิตต่อ VU เมื่อ Rt = 54.25 ms"
  ในบทที่ 2 ซึ่งเป็นต้นทางของค่าประเภทนี้:

      think time   iteration_duration   TPS ต่อ 1 VU   10 VUs ให้ TPS
          0 ms            54.25 ms           18.43          184.33
         50 ms           104.25 ms            9.59           95.92   ← แถวที่ใช้
        500 ms           554.25 ms            1.80           18.04
       1000 ms          1054.25 ms            0.95            9.49   ← ค่าที่เผลอหยิบมา

  ความผิดพลาดคือหยิบ 9.49 ซึ่งเป็นค่าของแถว Tt = 1000 ms (และเป็นยอดของ 10 VU
  ไม่ใช่ค่าต่อ VU) มาใช้กับบริบท Tt = 50 ms ซึ่งต้องเป็น 9.59 (1000 ÷ 104.25)
