อ้างอิง

สคริปต์ตัวอย่าง 5 แบบ

สคริปต์ทั้งห้าตัวนี้เป็นโค้ด k6 จริงที่รันได้ ไม่ใช่โครงร่าง ทุกไฟล์มีกลไกตรวจปลายทางก่อนเริ่มรัน ถ้าปลายทางไม่อยู่ในรายการที่อนุญาต สคริปต์จะหยุดทันที โดยไม่สร้างโหลดใด ๆ

ทฤษฎี: บทที่ 5
ปลายทาง: localhost:8080 หรือ test.k6.io
อ่านก่อนรันสคริปต์ใด ๆ

สคริปต์เหล่านี้ตั้งค่าเริ่มต้นให้ยิงไปที่ http://localhost:8080 เท่านั้น และยอมรับ test.k6.io เป็นทางเลือกที่สอง ถ้าต้องการยิงไปที่อื่น ต้องตั้ง ALLOW_ANY_TARGET=1 และคุณต้องมีสิทธิ์ทดสอบระบบนั้นจริง

การยิงโหลดใส่ระบบของผู้อื่นโดยไม่ได้รับอนุญาตเข้าข่ายการโจมตีและอาจผิดกฎหมาย ให้ใช้สภาพแวดล้อมทดสอบแทนระบบที่ผู้ใช้จริงใช้งานอยู่เสมอ และแจ้งผู้ดูแลระบบปลายทางล่วงหน้าทุกครั้ง

เตรียมปลายทางสำหรับฝึก

โปรเจกต์นี้แนบ mock server ที่ไม่ต้องติดตั้งอะไรเพิ่ม มันมี latency จำลองและมีจุดทดลอง ครบพอสำหรับฝึกทุกบท ลองเปิดดูก่อนว่ามีเส้นทางอะไรให้ใช้บ้าง

เปิด mock server (ไม่ต้องใช้ dependency ภายนอก) 
# รันจากโฟลเดอร์ loadtest-k6
node mock-server/server.mjs

# ตรวจว่าเปิดได้แล้ว
curl -i http://localhost:8080/api/items

# เส้นทางที่มีให้ทดลอง
#   GET /health                    ตรวจว่ายังทำงานอยู่
#   GET /api/items                 รายการสินค้า 20 ชิ้น
#   GET /api/items/{id}            สินค้ารายชิ้น
#   GET /api/always-404            ตอบ 404 ทุกครั้ง (สำหรับทดสอบ expected_response)
#   GET /api/toggle-slow           สลับโหมดช้า (+400 ms)
#   GET /api/toggle-fail?rate=0.2  ตั้งอัตราความล้มเหลวจำลอง

ภาพรวมสคริปต์ทั้งห้า

สคริปต์ตัวอย่าง ไฟล์ จุดประสงค์ และระยะเวลาที่ใช้
ไฟล์ จุดประสงค์ รูปแบบภาระ ใช้เวลา เกณฑ์ที่ตั้งไว้
smoke.js ยืนยันว่าสคริปต์ถูกและปลายทางตอบได้ 2 VU คงที่ 20 วินาที เพดานสุขภาพ p(95) ต่ำกว่า 1000 ms, ความผิดพลาดต่ำกว่า 1%, check ผ่านเกิน 99% (smoke ไม่ได้ตัดสิน SLO)
load.js วัดที่ภาวะใช้งานตามที่คาดไว้ ramping-vus ขึ้นถึง 10 VU แล้วถือไว้ 12 นาที p(95) ต่ำกว่า 500 ms, p(99) ต่ำกว่า 1500 ms, ความผิดพลาดต่ำกว่า 1%
stress.js หาจุดอิ่มตัวและดูว่าระบบพังแบบไหน ไต่ขึ้นเป็นขั้นถึง 4 เท่าของภาวะปกติ 17 นาที ความผิดพลาดต่ำกว่า 5% พร้อมหยุดอัตโนมัติถ้าเกิน
spike.js ดูการรับภาระกระชากและการฟื้นตัว กระชากจาก 5 ขึ้น 50 VU ใน 20 วินาที 9 นาที ความผิดพลาดต่ำกว่า 10%, p(95) ต่ำกว่า 3000 ms
soak.js หารอยรั่วหน่วยความจำและการเสื่อมสภาพ ถือ 10 VU ต่อเนื่อง 1 ชั่วโมง 4 นาที p(95) ต่ำกว่า 500 ms, p(99) ต่ำกว่า 1000 ms, ความผิดพลาดต่ำกว่า 1%

กายวิภาคของสคริปต์ k6

สคริปต์ที่แสดงด้านล่างคือ examples/load.js ตัวเดียวกับที่อยู่ในรายการทั้งห้า ดึงไฟล์จริงมาแสดงแล้วติดหมายเลข ①–⑨ ไว้ที่ต้นบรรทัด สคริปต์นี้จึงรันได้จริงตามที่เป็น และคำอธิบายแต่ละหมายเลขอยู่ใต้โค้ด บอกว่าเหตุใดบรรทัดนั้นจึงต้องมี ไม่ใช่แค่ว่ามันคืออะไร

กำลังอ่านไฟล์ examples/load.js

  1. ①บรรทัด import — k6 รันสคริปต์เป็นโมดูล จึงต้องประกาศว่าใช้ฟังก์ชันจากโมดูลใด การอ่านรายการนี้บอกได้ทันทีว่าสคริปต์แตะอะไรได้บ้าง และทำให้ตรวจสคริปต์ได้ก่อนรัน โดยยังไม่ต้องยิงคำขอออกไปแม้แต่คำขอเดียว
  2. ②ค่าตั้งต้นจาก __ENV — ปลายทางและจำนวน VU ต้องเปลี่ยนได้โดยไม่แก้ไฟล์ มิฉะนั้นสคริปต์เดียวจะใช้ได้กับสภาพแวดล้อมเดียว k6 มองเห็นตัวแปรสภาพแวดล้อมของเชลล์ทั้งหมดผ่าน __ENV และค่าเริ่มต้นชี้ที่ localhost เพื่อไม่ให้เผลอยิงออกอินเทอร์เน็ต
  3. ③ด่านตรวจปลายทาง — ฟังก์ชันนี้ทำงานตอนโหลดสคริปต์ ก่อนสร้าง VU ตัวแรก ถ้าปลายทางไม่อยู่ในรายการที่อนุญาตจะหยุดทันทีโดยไม่เกิดโหลด เป็นการกันความผิดพลาดที่แพงที่สุด คือการยิงโหลดใส่ระบบของคนอื่น
  4. ④metric ที่กำหนดเอง — Trend เก็บการกระจายของค่าที่เราสนใจ ส่วน Rate เก็บสัดส่วน ทั้งสองเป็น metric ที่ k6 ไม่รู้จักเอง จึงจำเป็นเมื่อคำถามไม่ใช่ "HTTP เร็วไหม" แต่เป็น "ขั้นตอนของเราช้าไหม" และทำให้ตั้ง threshold เฉพาะทางได้ ซึ่งอธิบายไว้ในบทที่ 3
  5. ⑤options คือ load model — ทั้งก้อนนี้คือรูปของการทดสอบ เริ่มที่ 0 VU ไต่ขึ้นเป็นขั้น ถึง 10 VU แล้วถือไว้ 8 นาที ก่อนลดลง เหตุผลที่ต้องไต่ขึ้นคือ cache และ connection pool ต้องมีเวลาอุ่นเครื่อง ไม่งั้นช่วงนาทีแรก จะสะท้อนสภาพระบบที่ยังไม่พร้อม วิธีเลือกรูปแบบอยู่ในบทที่ 5
  6. ⑥threshold คือเกณฑ์ตัดสิน — ที่นี่ที่เดียวที่ SLO กลายเป็นเกณฑ์ที่ตัดสินได้ ตัวเลข p(95)<500 ไม่ได้เปลี่ยนวิธีที่ k6 วัด แต่เปลี่ยนว่าการรันนี้ผ่านหรือไม่ผ่าน คู่กับ abortOnFail และ delayAbortEval เพื่อให้หยุดเองเมื่อแย่เกินเกณฑ์ โดยไม่ถูกตัดจบตั้งแต่ช่วงไต่ขึ้น
  7. ⑦VU รัน default() เป็นลูป — นี่คืองานที่ VU แต่ละตัวทำซ้ำ k6 เรียกฟังก์ชันนี้ใหม่ทันทีที่รอบก่อนจบ จำนวนรอบต่อวินาทีจึงขึ้นกับว่าในฟังก์ชันนี้ใช้เวลาไปเท่าไร ไม่ได้ขึ้นกับจำนวน VU เพียงอย่างเดียว
  8. ⑧check ไม่ใช่ threshold — check ตอบว่า "คำตอบตรงตามที่คาดไหม" แล้วบันทึกผลลง metric checks แต่ไม่ทำให้การรันล้มเหลว ต่างจาก threshold ที่ตัดสินผ่านหรือไม่ผ่าน การมี check จึงยังไม่พอถ้าไม่มีเกณฑ์มาบังคับ
  9. ⑨sleep คือ think time — เลียนแบบผู้ใช้ที่อ่านข้อมูลก่อนกดอะไรต่อไป และถูกนับรวมใน iteration_duration ถ้าถอดบรรทัดนี้ออก ตัวเลข throughput จะสูงขึ้นทันทีโดยที่เซิร์ฟเวอร์ไม่ได้เร็วขึ้นเลย ซึ่งเป็นวิธีสร้าง "โหลดปลอม" ที่พบบ่อยที่สุด
กำลังอ่านไฟล์สคริปต์

วิธีรันแบบติดตั้งในเครื่อง

คำสั่งรันสคริปต์ด้วย k6 ที่ติดตั้งในเครื่อง 
# 1) เปิด mock server ไว้ในเทอร์มินัลหนึ่ง
node mock-server/server.mjs

# 2) เปิดอีกเทอร์มินัล แล้วรันตามลำดับนี้เสมอ
cd loadtest-k6

# ยืนยันว่าทุกอย่างพร้อม — ใช้เวลา 20 วินาที
k6 run -e BASE_URL=http://localhost:8080 examples/smoke.js

# วัดที่ภาวะเป้าหมาย — 12 นาที
k6 run -e BASE_URL=http://localhost:8080 examples/load.js

# หาจุดอิ่มตัว — 17 นาที
k6 run -e BASE_URL=http://localhost:8080 -e BASE_VUS=5 examples/stress.js

# ดูการรับภาระกระชาก — 9 นาที
k6 run -e BASE_URL=http://localhost:8080 -e SPIKE_VUS=30 examples/spike.js

# หาปัญหาระยะยาว — ปรับให้สั้นลงได้ด้วย HOLD
k6 run -e BASE_URL=http://localhost:8080 -e VUS=5 -e HOLD=10m examples/soak.js

# เทียบกับปลายทางสาธารณะที่ทำไว้สำหรับทดสอบโดยเฉพาะ
k6 run -e BASE_URL=https://test.k6.io examples/smoke.js

ทุกสคริปต์อ่านค่าจากตัวแปรสภาพแวดล้อม ทำให้ไม่ต้องแก้ไฟล์เมื่อเปลี่ยนปลายทาง ค่าที่รับได้คือ BASE_URL, TARGET_PATH, PEAK_VUS, BASE_VUS, NORMAL_VUS, SPIKE_VUS, VUS และ HOLD

ทำไมชื่อตัวแปรจึงเป็น TARGET_PATH ไม่ใช่ PATH

k6 มองเห็นตัวแปรสภาพแวดล้อมทั้งหมดของเชลล์ผ่านออบเจกต์ __ENV ดังนั้นถ้าตั้งชื่อตัวแปรว่า PATH มันจะชนกับตัวแปร PATH ของระบบปฏิบัติการซึ่งมีอยู่แล้วเสมอ ค่าที่ได้จึงกลายเป็นรายการพาธของคำสั่ง แทนที่จะเป็นพาธของ API ทำให้คำขอไปผิดที่และได้ 404 โดยไม่มีคำเตือนใด ๆ ตัวอย่างสคริปต์จึงตั้งชื่อให้เฉพาะเจาะจงว่า TARGET_PATH หลักปฏิบัติทั่วไปคือตั้งชื่อตัวแปรให้มีคำนำหน้าเฉพาะโปรเจกต์ เช่น APP_ หรือ LT_

วิธีรันแบบ Docker

ถ้าไม่อยากติดตั้ง k6 ในเครื่อง ให้ใช้ image ทางการ สิ่งที่ต้องระวังคือ จากในคอนเทนเนอร์ localhost หมายถึงตัวคอนเทนเนอร์เอง ไม่ใช่เครื่องของคุณ จึงต้องใช้ host.docker.internal แทน

รันด้วย Docker image ทางการ 
# รันจากโฟลเดอร์ loadtest-k6
# บน macOS และ Windows ใช้ host.docker.internal เพื่อออกมาหาเครื่องแม่

docker run --rm -i grafana/k6 run \
  -e BASE_URL=http://host.docker.internal:8080 \
  - < examples/smoke.js

# ถ้าเปิด mock server ไว้ในคอนเทนเนอร์ด้วยกัน ให้ใช้ชื่อบริการแทน
# docker network create loadtest
# docker run -d --name mock --network loadtest -p 8080:8080 -v "$PWD":/app -w /app node:22 node mock-server/server.mjs
# docker run --rm -i --network loadtest grafana/k6 run -e BASE_URL=http://mock:8080 - < examples/load.js

# เก็บผลลัพธ์ออกมาเป็นไฟล์บนเครื่อง
docker run --rm -i -v "$PWD:/work" -w /work grafana/k6 run \
  --summary-export=summary.json \
  -e BASE_URL=http://host.docker.internal:8080 \
  - < examples/load.js

บน Linux ให้เพิ่ม --add-host=host.docker.internal:host-gateway ให้กับคำสั่ง docker run เพราะชื่อนี้ไม่มีมาให้โดยอัตโนมัติ

สิ่งที่ควรดูหลังรันแต่ละตัว

จุดที่ต้องสังเกตของสคริปต์แต่ละตัว
สคริปต์ สิ่งที่ต้องดู ถ้าพบสิ่งนี้ให้ทำอะไร
smoke.js check ต้องผ่าน 100% และ http_req_failed เป็น 0 ถ้าไม่ผ่าน อย่ารันตัวอื่นต่อ ให้แก้สคริปต์หรือปลายทางก่อน
load.js ช่วง 5 นาทีกลางที่ VU คงที่ ดูว่า p(95) แบนหรือค่อย ๆ ไต่ขึ้น ถ้าไต่ขึ้นเรื่อย ๆ แสดงว่ายังไม่ถึงภาวะคงตัว หรือมีคิวสะสม
stress.js ขั้นที่ throughput หยุดโต แต่ p(95) เริ่มพุ่ง บันทึกจำนวน VU ที่ขั้นก่อนหน้าจุดนั้นไว้เป็นความจุที่ยอมรับได้
spike.js ช่วง 3 นาทีหลังกระชาก ว่า p(95) กลับสู่ระดับเดิมหรือยัง ถ้ากลับไม่ทันภายในไม่กี่นาที แปลว่าระบบระบายคิวช้า
soak.js เทียบ p(95) ชั่วโมงแรกกับชั่วโมงสุดท้าย ถ้าชั่วโมงหลังสูงกว่าชัดเจน ให้สงสัยรอยรั่วหรือทรัพยากรที่ไม่ได้คืน

ดาวน์โหลดไฟล์

ดาวน์โหลดไฟล์ไปวางในโปรเจกต์ของคุณได้โดยตรง ลิงก์ด้านล่างชี้ไปที่ไฟล์จริงในโฟลเดอร์ examples/ ซึ่งเป็นไฟล์ชุดเดียวกับที่แสดงในหน้านี้ จึงไม่มีทางที่โค้ดบนหน้าจะไม่ตรงกับไฟล์

ขั้นต่อไป

  • อ่านวิธีอ่านผลลัพธ์ของสคริปต์เหล่านี้ได้ที่ บทที่ 6
  • ดูว่าตัวเลข p95 กับ p99 ของผลลัพธ์ทำงานอย่างไรได้ที่ บทที่ 4
  • คำนวณล่วงหน้าว่าจะต้องใช้ VU เท่าไรได้ที่ เครื่องคำนวณ
  • ถ้าต้องเลือกจำนวน VU ให้เหมาะกับระบบของคุณ เริ่มจาก บทที่ 5 ซึ่งอธิบายวิธีหาแบบเป็นขั้น
