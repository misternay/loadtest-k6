อ้างอิง

แก้ปัญหาที่พบบ่อย

ปัญหายี่สิบข้อที่เจอบ่อยที่สุดเมื่อใช้ k6 จัดกลุ่มตามอาการ แต่ละข้อมีอาการที่เห็นบนหน้าจอ สาเหตุที่เป็นไปได้ และวิธีแก้ที่ทำตามได้ทันที

ใจความสำคัญ

  1. สาเหตุร่วมที่พบบ่อยคือใช้สิ่งที่ k6 ไม่มี เช่น require() ของ Node หรือหน่วยเวลาแบบคำเต็ม จึงควรตรวจด้วย k6 inspect script.js ก่อนยิงโหลดจริง
  2. ตัวเลขที่ดูดีไม่ได้แปลว่าเชื่อถือได้ ต้องดู http_req_failed, dropped_iterations และบรรทัด running ประกอบเสมอ
  3. ถ้าเพิ่ม VU แล้วอัตราคำขอไม่ขยับ แต่ CPU ของเครื่องที่รัน k6 แตะ 100% แปลว่าเครื่องทดสอบเป็นคอขวด ไม่ใช่ระบบปลายทาง
วิธีใช้หน้านี้

กดหัวข้อเพื่อเปิดอ่านรายละเอียด กล่องสีเทาคือข้อความที่มักเห็นบนหน้าจอจริง ให้เทียบกับสิ่งที่คุณเห็น ถ้าตรงกันเลยให้ทำตามหัวข้อนั้น ถ้าไม่ตรง ให้ดูกลุ่มที่ใกล้เคียงที่สุดก่อน เพราะหลายอาการมีสาเหตุร่วมกัน

หมายเหตุเล็กน้อย: ในกล่องข้อความ k6 จะพิมพ์เครื่องหมายถูกและกากบาทกำกับบรรทัดที่ตั้งเกณฑ์ไว้ หน้านี้เขียนเป็นคำว่า "ผ่าน" และ "ไม่ผ่าน" แทน เพื่อให้อ่านออกด้วยโปรแกรมอ่านหน้าจอ และเพื่อไม่ให้ปะปนกับสัญลักษณ์อื่น ส่วนข้อความอื่นในกล่องเป็นไปตามที่ k6 พิมพ์จริง

ก่อนแก้ปัญหาด้วยการเพิ่มจำนวน VU

เกือบทุกอาการในกลุ่ม "ผลลัพธ์ดูแปลก" ไม่ได้แก้ได้ด้วยการเพิ่ม VU การเพิ่ม VU ตอนที่ยังไม่รู้สาเหตุจะยิ่งรบกวนระบบปลายทางและทำให้อ่านผลยากขึ้น ให้แก้ที่สาเหตุก่อน แล้วค่อยกลับไปวัดใหม่

ก่อนอ่านตัวเลขประสิทธิภาพใด ๆ ให้ตรวจสามอย่างนี้ก่อน — บรรทัด running, dropped_iterations และอัตราความผิดพลาด ถ้าสามอย่างนี้ยังไม่สะอาด ตัวเลขที่เหลือยังใช้ตัดสินผลไม่ได้

กลุ่มที่ 1 — ติดตั้งและรันสคริปต์

1. รันแล้วขึ้นว่าไม่รู้จักคำสั่ง k6
อาการที่เห็น 
zsh: command not found: k6
สาเหตุที่เป็นไปได้
  • ยังไม่ได้ติดตั้ง k6
  • ติดตั้งแล้ว แต่ไบนารีไม่อยู่ใน PATH ของเชลล์
  • เปิดเทอร์มินัลค้างไว้ตั้งแต่ก่อนติดตั้ง
วิธีแก้
  1. ตรวจด้วย which -a k6 ถ้าไม่พบคือไม่มีใน PATH
  2. ติดตั้งตามคู่มือทางการที่ grafana.com/docs/k6 — install
  3. เปิดเทอร์มินัลใหม่หนึ่งครั้ง
  4. ถ้าใช้ Docker ให้เรียกผ่าน docker run --rm -i grafana/k6 run - <script.js
2. k6 อ่านสคริปต์ไม่ผ่านด้วยข้อผิดพลาดทางไวยากรณ์
อาการที่เห็น 
ERRO[0000] SyntaxError: Unexpected token (3:14)
	at go.k6.io/k6/js/modules/...
สาเหตุที่เป็นไปได้
  • ใช้ require() ของ Node ซึ่ง k6 ไม่รองรับ ต้องใช้ import
  • เรียกไลบรารีของ Node เช่น fs, path, crypto
  • ลืมปิดวงเล็บหรือปีกกาใน options
วิธีแก้
  1. เปลี่ยน require('k6/http') เป็น import http from 'k6/http'
  2. แทนไลบรารีของ Node ด้วยโมดูล k6 เช่น k6/crypto
  3. ตรวจไวยากรณ์ก่อนรันด้วย k6 inspect script.js
3. สคริปต์รันจบในเสี้ยววินาทีและไม่มีข้อมูลอะไรเลย
อาการที่เห็น 
iteration_duration.............: avg=0s min=0s med=0s max=0s
iterations.....................: 0      0/s
running (0.0s), 0/10 VUs
สาเหตุที่เป็นไปได้
  • ฟังก์ชันที่ส่งออกไม่ชื่อ default
  • options ไม่ได้ถูกส่งออก หรือไม่มี scenario ที่ทำงานจริง
  • duration เป็นค่าว่างหรือตีความเป็นศูนย์
วิธีแก้
  1. ตรวจว่าฟังก์ชันเขียนว่า export default function ()
  2. ตรวจว่า options ถูกส่งออกด้วยคำว่า export
  3. รัน k6 inspect script.js แล้วดูว่าค่า options ตรงกับที่ตั้งใจ
  4. เพิ่ม console.log('รอบทำงาน') บรรทัดแรกในฟังก์ชัน
4. ตั้งค่า duration หรือ stages แล้ว k6 บอกว่าแปลงค่าไม่ได้
อาการที่เห็น 
ERRO[0000] invalid duration "5 minutes"
ERRO[0000] unknown executor "rampingVUs"
สาเหตุที่เป็นไปได้
  • เขียนหน่วยเวลาเป็นคำเต็ม เช่น '5 minutes'
  • ใช้ชื่อ executor ผิดรูปแบบ เช่น rampingVUs
  • ใส่จำนวน VU เป็นสตริงใน stages
วิธีแก้
  1. ใช้หน่วยย่อ ms, s, m, h ติดกับตัวเลข เช่น '5m'
  2. ใช้ชื่อ executor ตามที่กำหนด เช่น 'ramping-vus', 'constant-arrival-rate' ตามตารางใน บทที่ 2
  3. ค่า target ต้องเป็นตัวเลขไม่ใส่เครื่องหมายคำพูด เช่น { duration: '1m', target: 10 }

กลุ่มที่ 2 — เครือข่ายและการเชื่อมต่อ

5. ต่อปลายทางไม่ได้ ทุกคำขอและทุก VU ล้มเหลวเหมือนกันหมด
อาการที่เห็น 
WARN[0001] Request Failed  error="Get \"http://localhost:8080/api/items\": dial tcp 127.0.0.1:8080: connect: connection refused"
http_req_failed................: 100.00% ล้มเหลว 1155
สาเหตุที่เป็นไปได้
  • ปลายทางไม่ได้ทำงานอยู่
  • รันปลายทางคนละพอร์ตกับสคริปต์
  • ค่าที่ส่งด้วย -e BASE_URL=… ไม่ถูกอ่าน เพราะสะกดชื่อไม่ตรง
  • ปลายทางผูกกับที่อยู่เฉพาะเครื่อง แต่สคริปต์ยิงไปชื่อโฮสต์อื่น
วิธีแก้
  1. ตรวจว่าปลายทางตอบจริงด้วย curl -i http://localhost:8080/api/items
  2. ถ้าใช้ mock server ให้รัน node mock-server/server.mjs แล้วดูพอร์ตที่ฟังอยู่
  3. ตรวจว่าชื่อคีย์ที่ส่งตรงกับที่สคริปต์อ่าน เช่น __ENV.BASE_URL คู่กับ -e BASE_URL=…
  4. พิมพ์ console.log(BASE_URL) บรรทัดแรกเพื่อยืนยันว่าค่ามาถึงจริง
6. บางคำขอหมดเวลา แต่ปลายทางยังทำงานอยู่
อาการที่เห็น 
error="Get \"…\": context deadline exceeded"
http_req_duration..............: avg=60.00s  max=60.00s
สาเหตุที่เป็นไปได้
  • หมดเวลารอตามค่าเริ่มต้น 60 วินาที
  • ตั้ง timeout ของคำขอสั้นเกินไป
  • มี proxy หรือ load balancer ตัดการเชื่อมต่อก่อน
วิธีแก้
  1. ดูว่า http_req_duration เท่ากับเพดานเวลาพอดีไหม ถ้าเท่ากันคือหมดเวลา
  2. ตั้งเวลารอให้เหมาะกับงาน เช่น http.get(url, { timeout: '10s' })
  3. ยิงด้วย curl -w '%{time_total}' ถ้า curl เร็วแต่ k6 ช้า ให้ตรวจว่ามีอะไรอยู่ระหว่างทาง
7. ขึ้นข้อผิดพลาดเรื่องใบรับรอง TLS เมื่อยิงไปที่ https
อาการที่เห็น 
error="Get \"https://…\": tls: failed to verify certificate: x509: certificate signed by unknown authority"
สาเหตุที่เป็นไปได้
  • ปลายทางใช้ใบรับรองที่ออกเอง (self-signed)
  • ชื่อโฮสต์ไม่ตรงกับชื่อในใบรับรอง
  • เครื่องยังไม่ได้ติดตั้ง certificate authority ภายในองค์กร
วิธีแก้
  1. ติดตั้ง certificate authority ขององค์กรลงในที่เก็บของระบบ
  2. ถ้าเป็นสภาพแวดล้อมทดสอบในเครื่อง ใช้ k6 run --insecure-skip-tls-verify script.js
  3. ตรวจว่า --insecure-skip-tls-verify ให้ผลจริง จาก http_req_tls_handshaking
  4. ห้ามใช้กับระบบจริงเด็ดขาด
8. รันด้วย VU มาก ๆ แล้วขึ้นว่าเปิดไฟล์หรือ socket เกินขีดจำกัด
อาการที่เห็น 
WARN[0012] Request Failed  error="…: socket: too many open files"
http_req_blocked...............: avg=12.50ms max=340.00ms
สาเหตุที่เป็นไปได้
  • ขีดจำกัดไฟล์ที่โปรเซสเปิดได้ (file descriptor) ต่ำกว่าจำนวน connection
  • ใช้ --no-connection-reuse ทำให้เปิด connection ใหม่ทุกคำขอ
วิธีแก้
  1. ดูขีดจำกัดด้วย ulimit -n แล้วเพิ่มด้วย ulimit -n 65535 ก่อนรัน k6
  2. ยกเลิก --no-connection-reuse ถ้าไม่ได้ตั้งใจทดสอบการเปิด connection ใหม่
  3. ดูว่า http_req_blocked สูงขึ้นตามจำนวน VU ไหม ถ้าใช่ เครื่องทดสอบเป็นคอขวด ต้องลด VU

กลุ่มที่ 3 — ผลลัพธ์ดูแปลก

9. อัตราความล้มเหลวสูงมาก ทั้งที่เปิดเว็บด้วยเบราว์เซอร์ได้ปกติ
อาการที่เห็น 
http_req_failed................: 100.00% ล้มเหลว 1155 จาก 1155
http_req_duration..............: avg=3.20ms  p(95)=4.10ms
สาเหตุที่เป็นไปได้
  • คำขอได้สถานะ 4xx ซึ่ง k6 นับเป็นความล้มเหลว
  • ยิงไปพาธที่ไม่มีอยู่ หรือไม่ได้ส่งข้อมูลยืนยันตัวตน
วิธีแก้
  1. ดูรหัสสถานะจากคำขอแรกด้วย console.log(res.status) ว่าเป็น 401, 403, 404 หรือ 500
  2. ถ้าเป็น 401 หรือ 403 ให้ตรวจส่วนหัวการยืนยันตัวตน
  3. ถ้าเป็น 404 ให้ตรวจพาธและวิธี HTTP
  4. ถ้าเป็นผลที่ตั้งใจ ให้ใส่แท็ก expected_response: 'true' แล้วเขียน check() ยืนยันรหัสที่คาดไว้เอง
10. เวลาตอบสนองดูดีเกินจริง จนไม่น่าเชื่อ
อาการที่เห็น 
http_reqs......................: 500    50.00/s
http_req_duration..............: avg=0.10ms  p(95)=0.15ms
data_received..................: 0 B    0 B/s
สาเหตุที่เป็นไปได้
  • ปลายทางตอบข้อผิดพลาดเร็ว ๆ เช่น 404 หรือ 301
  • ยิงไปแคชหรือ proxy ที่ใกล้กว่าเดิม
  • คำขอไม่ได้ออกจากเครื่อง เช่นถูกเปลี่ยนทางไป localhost
วิธีแก้
  1. ดู data_received ถ้าเป็นศูนย์ต่อคำขอ แปลว่าไม่ได้ข้อมูลกลับมา
  2. ดู http_req_failed ประกอบ ถ้าสูงพร้อม latency ต่ำมาก แปลว่าวัดการตอบปฏิเสธ
  3. เขียน check() ยืนยันทั้งรหัสสถานะและเนื้อหา
11. ไม่เห็นค่า p99 ในสรุปผลท้ายการรัน
อาการที่เห็น 
http_req_duration..............: avg=54.25ms min=4.21ms med=44.40ms max=584.70ms p(90)=65.31ms p(95)=74.53ms
(ไม่มี p(99) ในบรรทัดนี้)
สาเหตุที่เป็นไปได้
  • เป็นพฤติกรรมปกติ สรุปผลมาตรฐานแสดงเพียง avg, min, med, max, p(90), p(95)
  • ยังไม่ได้ตั้ง threshold ที่อ้างถึงเปอร์เซ็นไทล์นั้น
วิธีแก้
  1. ตั้ง threshold ที่อ้างถึงค่านั้น เช่น http_req_duration: ['p(99)<1500'] แล้ว k6 จะพิมพ์ค่า p(99) ในบล็อกเกณฑ์
  2. หรือส่งออกข้อมูลดิบด้วย -o csv=raw.csv แล้วคำนวณเอง เป็นวิธีที่ยืดหยุ่นที่สุด และใช้สร้างข้อมูลใน บทที่ 4
  3. ใช้ -o json=raw.json ถ้าต้องการแท็กครบสำหรับกรอง
12. จำนวน iterations ไม่เท่ากับจำนวน http_reqs
อาการที่เห็น 
http_reqs......................: 3465   280.32/s
iterations.....................: 1155   93.44/s
สาเหตุที่เป็นไปได้
  • หนึ่งรอบของ default() ยิงหลายคำขอ เป็นเรื่องปกติ
  • คำขอจาก setup() ถูกนับใน http_reqs แต่ไม่นับเป็นรอบ
วิธีแก้
  1. คำนวณ http_reqs ÷ iterations เพื่อดูว่าหนึ่งรอบยิงกี่คำขอ แล้วใช้ในสูตร TPS ตาม บทที่ 1
  2. แยกคำขอด้วย group() และแท็ก name เพื่อดูว่าเวลาไปอยู่ขั้นตอนใด
  3. รายงานทั้ง TPS และจำนวนคำขอต่อรอบคู่กัน
13. จำนวน VU ที่ทำได้จริงต่ำกว่าที่ตั้งไว้
อาการที่เห็น 
vus............................: 4      min=4      max=4
vus_max........................: 100    min=100    max=100
dropped_iterations.............: 8420   702.10/s
สาเหตุที่เป็นไปได้
  • ใช้ executor แบบ arrival-rate ที่ตั้ง maxVUs ไว้ไม่พอ
  • แต่ละ VU ใช้เวลานานขึ้น
  • เครื่องทดสอบจำกัดหน่วยความจำหรือ connection
วิธีแก้
  1. ถ้า dropped_iterations มากกว่า 0 แปลว่าสร้างโหลดได้ต่ำกว่าแผน ต้องแก้ก่อนใช้ผล
  2. เพิ่ม maxVUs ให้สูงพอ แล้วรันใหม่ดูว่ายังเป็นศูนย์ไหม
  3. ถ้ายังทิ้งรอบ ให้เพิ่ม preAllocatedVUs
  4. ถ้าเครื่องทดสอบเป็นคอขวด ให้ลดอัตราเป้าหมาย

กลุ่มที่ 4 — threshold ไม่ผ่าน

14. threshold ไม่ผ่านทั้งที่ตัวเลขดูดี
อาการที่เห็น 
http_req_duration..............: avg=120.00ms p(95)=480.00ms
  ไม่ผ่าน { p(95)<500 }........: 520.00ms
ERRO[0015] some thresholds have failed
exit status 99
สาเหตุที่เป็นไปได้
  • ช่วงอุ่นเครื่องและช่วงไต่ขึ้นมีค่าสูง และยังถูกนับรวมในการตัดสิน
  • อ่านค่าเฉลี่ยแล้วคิดว่าผ่าน แต่เกณฑ์อยู่ที่เปอร์เซ็นไทล์
  • ตั้งเกณฑ์เข้มเกิน SLO
วิธีแก้
  1. แยกช่วงภาวะคงตัวเป็น scenario ของตัวเอง (มี startTime) แล้วตั้ง threshold แบบอ้างแท็ก เช่น 'http_req_duration{scenario:steady}': ['p(95)<500']
  2. กรองเฉพาะช่วงภาวะคงตัวจากไฟล์ที่ส่งออกไว้
  3. ถ้าปัญหาคือ k6 ตัดจบเร็วเกินไป ให้ใช้ delayAbortEval คู่กับ abortOnFail: true ในรูปแบบยาวของ threshold เช่น delayAbortEval: '180s' — ตัวเลือกนี้เลื่อนเวลาที่จะตัดสินใจหยุดเท่านั้น ไม่ได้ตัดข้อมูลช่วงอุ่นเครื่องออกจากการคิดค่า threshold และ delayAbortedCheck ไม่มีใน k6 v2.2.0
  4. ตรวจว่าเกณฑ์ตรงกับ SLO จริง ถ้า SLO เขียน p95 ต่ำกว่า 300 ก็ไม่ควรตั้ง 500
15. เกณฑ์บนอัตราความล้มเหลวไม่เคยผ่าน แม้ค่าดูเป็นศูนย์
อาการที่เห็น 
http_req_failed................: 0.00%   ล้มเหลว 0 จาก 1,155
  ไม่ผ่าน { rate>1 }...........: 0.00%
ERRO[0015] some thresholds have failed
สาเหตุที่เป็นไปได้
  • เขียน rate<1 โดยคิดว่า 1 คือ 1% ทั้งที่จริงคือ 100%
  • กลับด้านเครื่องหมายเป็น > แทน <
  • ตั้งเกณฑ์บน checks ทั้งที่สคริปต์ไม่มี check()
วิธีแก้
  1. metric ชนิด Rate เก็บเป็นสัดส่วนทศนิยม 1% จึงเขียนเป็น 0.01
  2. ใช้เครื่องหมาย < เสมอสำหรับเพดานที่ห้ามเกิน
  3. ถ้าตั้งเกณฑ์บน checks ต้องมี check() จริง
16. k6 ฟ้องว่าไวยากรณ์ของ threshold ไม่ถูกต้อง
อาการที่เห็น 
ERRO[0000] invalid threshold: "p (95) < 500"
ERRO[0000] invalid threshold: "p95<500"
สาเหตุที่เป็นไปได้
  • ใส่ช่องว่างในนิพจน์
  • เขียน p95 โดยไม่มีวงเล็บ
  • ใช้ชื่อเปอร์เซ็นไทล์ที่ k6 ไม่รู้จัก เช่น p(95.5)
วิธีแก้
  1. เขียนให้ไม่มีช่องว่าง รูปแบบที่ถูกคือ 'p(95)<500'
  2. ใช้ตัวเลขเปอร์เซ็นไทล์ที่ k6 รองรับ เช่น 50, 90, 95, 99, 99.9
  3. ถ้าต้องการค่าเฉลี่ยให้ใช้ชื่อ avg เช่น 'avg<500'
  4. ตรวจด้วย k6 inspect script.js ก่อนรันจริงทุกครั้ง

กลุ่มที่ 5 — เครื่องที่รัน k6 เป็นคอขวดเอง

17. CPU ของเครื่องที่รัน k6 แตะ 100% ระหว่างการทดสอบ
อาการที่เห็น 
เพิ่ม VU แล้ว http_reqs/s ไม่ขยับ แต่ CPU ของเครื่องรัน k6 อยู่ที่ 99-100%
พร้อมกับ dropped_iterations ที่เริ่มมากกว่า 0
สาเหตุที่เป็นไปได้
  • สคริปต์มีงานคำนวณหนัก เช่นประมวลผล JSON ก้อนใหญ่
  • VU สูงเกินกำลังเครื่องทดสอบ
  • รัน k6 บนเครื่องเดียวกับระบบปลายทาง
วิธีแก้
  1. ย้ายไปเครื่องที่ไม่มีงานอื่นทำ
  2. ย้ายการเตรียมข้อมูลไปไว้ในบริบท init
  3. ปิดการบันทึกผลที่ไม่จำเป็น และเลี่ยงการพิมพ์ log ทุกคำขอ
  4. ถ้ายังไม่พอ ให้กระจายไปหลายเครื่องและรวมผลเข้าที่เดียว
18. เครื่องรัน k6 หน่วยความจำเต็มเมื่อตั้ง VU จำนวนมาก
อาการที่เห็น 
ERRO[0042] the k6 process was killed (out of memory)
vus_max........................: 5000   min=5000   max=5000
สาเหตุที่เป็นไปได้
  • k6 จอง VU ตาม vus_max หรือ preAllocatedVUs ซึ่งกินหน่วยความจำจริง
  • โหลดข้อมูลก้อนใหญ่ในบริบท init ทุก VU จึงถือสำเนาของตัวเอง
  • จองเกินจำเป็น เช่นจอง 5,000 VU แต่ใช้จริงเพียง 20
วิธีแก้
  1. ลด preAllocatedVUs ให้ใกล้จำนวนที่ใช้จริง ใช้ maxVUs เป็นเพดานยามจำเป็น
  2. อ่านข้อมูลก้อนใหญ่ในบริบท init แล้วเก็บเฉพาะค่าที่ต้องใช้
  3. ตรวจว่า vus_max ใกล้เคียงกับ vus ที่ใช้จริง
19. ตัวเลขที่ได้ไม่ตรงกับที่คาดไว้เลยแม้จะตั้งค่าเหมือนเดิม
อาการที่เห็น 
การรันครั้งแรกได้ 93.44/s ครั้งถัดไปได้ 71.20/s โดยใช้คำสั่งเดิมทุกอย่าง
สาเหตุที่เป็นไปได้
  • มีงานอื่นรันบนเครื่องทดสอบหรือเครื่องปลายทาง
  • แคชอุ่นไม่เท่ากันในแต่ละรอบ
  • ข้อมูลทดสอบเปลี่ยนไป คำขอจึงไม่เท่าเดิม
วิธีแก้
  1. รันซ้ำอย่างน้อยสามครั้ง ถ้าแกว่งมากกว่า 20% ให้ตรวจสภาพแวดล้อมก่อน
  2. จดสภาพแวดล้อมทุกครั้ง ทั้งเครื่องที่รัน สาขา commit และช่วงเวลาที่รัน
  3. ใช้ smoke test ยืนยันว่าปลายทางตอบตรงกันก่อนทุกรอบ
  4. เปรียบเทียบตัวเลขระหว่างรอบด้วย --summary-export แทนการเทียบด้วยสายตา
20. จะรู้ได้อย่างไรว่าผลที่ได้เชื่อถือได้จริง
สัญญาณที่บอกว่าผลยังเชื่อถือไม่ได้ 
running (0.4s) — สั้นเกินกว่าจะมีความหมาย
dropped_iterations มากกว่า 0
http_req_failed สูงกว่า 1%
vus ที่ทำได้จริงต่ำกว่าที่ตั้งไว้
สาเหตุที่เป็นไปได้
  • รันสั้นเกินไปจนช่วงอุ่นเครื่องกินสัดส่วนมาก
  • โหลดที่ตั้งใจไว้ไม่ได้ถูกสร้างจริง
  • มีข้อผิดพลาดแต่ไม่มีเกณฑ์ใดจับได้
วิธีแก้
  1. ตั้งเกณฑ์ให้ครอบทุกด้านสำคัญ ได้แก่ http_req_duration บนเปอร์เซ็นไทล์, http_req_failed, checks และ dropped_iterations
  2. รันยาวพอให้ช่วงภาวะคงตัวกินเวลาอย่างน้อยห้านาที
  3. ตรวจสามอย่างก่อนอ่านตัวเลข คือบรรทัด running, dropped_iterations และอัตราความผิดพลาด

ถ้ายังแก้ไม่ได้

  1. ลดขนาดปัญหาให้เล็กที่สุด ใช้ 1 VU นาน 10 วินาที ถ้าอาการยังเกิดที่ขนาดนี้ ปัญหาอยู่ที่สคริปต์หรือปลายทาง
  2. ตัดสคริปต์ให้เหลือคำขอเดียว ลบ check, threshold และ custom metric ออกก่อน แล้วใส่กลับทีละอย่าง
  3. ยิงด้วย curl เทียบ ถ้า curl ได้แต่ k6 ไม่ได้ ปัญหาอยู่ที่สคริปต์ ถ้าไม่ได้ทั้งคู่ ปัญหาอยู่ที่เครือข่ายหรือปลายทาง
  4. เทียบกับสคริปต์ตัวอย่าง ใน หน้าสคริปต์ตัวอย่าง ซึ่งรันได้จริงกับ mock server ที่แนบมา ถ้าตัวอย่างรันได้ แต่ของคุณไม่ได้ ให้เทียบทีละบรรทัด
  5. อ่านเอกสารทางการ ที่ grafana.com/docs/k6 โดยค้นจากข้อความ error ที่เห็น
